# 数据模型与需求差距梳理

> 梳理日期：2026-11-05
> 对照基准：`docs/03-模块需求规格/` 9 份文档的「核心实体」声明 + 204 项功能点
> 实际模型：159 张表（含 45 张 Flowable 引擎表 `ACT_*`、26 张遗留库 `yunjian*`）
> 目的：在做 P1 功能前，先分清「写代码就能做」与「必须先改数据模型」

---

## 1. 结论摘要

差距分三类，严重程度依次递减：

| 类型 | 数量 | 影响 |
|---|---|---|
| **A. 缺表** | 11 处 | 对应功能无法实现，必须先建表 |
| **B. 缺字段** | 5 处 | 功能可做但能力降级（如查重少一个维度） |
| **C. 有表但设计不支持** | 5 处 | 功能能跑，但性能差 / 将来改造会静默失效 |

**一句话结论**：审计报告里 26 项 P1 未实现中，约一半卡在数据模型而非代码。先改模型的 4 张表（`att_holiday`、`cmp_exchange_rate`、`flow_ext_delegate`、`sys_notify_preference`）可解锁 6 个功能点，性价比最高。

`Regularization` / `Transfer` / `Termination`（三类异动）**不算缺表**，因为：

- 组织版本 → 用 `org_dept_history` 快照实现（见 §4 的局限）

这类「实体合并」是设计取舍而非缺陷，不应作为待办。

## 4. C 类：有表但设计不支持

这一类最容易被忽略——**功能能跑、测试也过，但在特定条件下会变慢或失效**。

### 4.1 查重字段无索引（本轮实际踩到）

| 表.字段 | 现状索引 | 后果 |
|---|---|---|
| `emp_employee.cert_no_cipher` | 无（仅 pinyin / status / emp_no） | 再入职查重**全表扫描** |
| `rcu_candidate.email` | 无（仅 status） | 候选人查重**全表扫描** |

两处都是本轮新做的功能。当前数据量（个位数员工/候选人）无感，但员工上万后
每次查重扫全表。**这是「能跑但会变慢」的典型，不会被测试发现。**

### 4.2 密文列存明文（结构性技术债）

`emp_employee.cert_no_cipher` / `mobile_cipher`、`rcu_candidate.mobile_cipher`
的写入都是 `setXxxCipher(req.xxx())` —— **调用方传什么就存什么，项目未接加密插件**
（`Employee` 类注释已声明）。

后果链：
1. 现在查重按明文等值可用
2. 一旦接入 ShardingSphere 或改随机 IV 加密，同值密文不同
3. **查重会返回空结果、不报错**，功能悄悄失效

修复不是"改代码"而是"加列 + 改查询 + 回填历史数据"，属数据迁移工程。

### 4.3 组织版本只覆盖部门

`org_dept_history` 只有部门快照。需求 ORG-F-004 要求「部门/岗位变更带生效日期，
未到日期为草稿版本，历史快照查询」——**岗位/职级无对应历史表**。

同时「草稿版本」这个状态在任何表里都不存在：`org_dept.effective_from` 只是
一个日期字段，没有「未生效 / 已生效」的状态机。

### 4.4 人才库是标签不是池

需求 `TalentPool` 应记录「淘汰/未入职沉淀、解冻投递」等状态，
实际只有 `rcu_talent_pool_tag`（标签表）。标签能分类，但存不了
「该候选人已解冻可再投递」这类状态。

### 4.5 流程阶段是流水不是定义

需求 `PipelineStage` 是「看板列定义」（新投递→初筛→面试→Offer→入职），
实际只有 `rcu_stage_log`（每次流转的流水）。看板列只能硬编码在前端，
无法按租户自定义阶段。

## 5. 差距对「未实现功能」的解释力

审计报告列出 P1 有 26 项未实现。按卡点分类：

| 卡点 | 项数 | 代表项 | 能否直接做 |
|---|---|---|---|
| **数据模型不支持** | 约 11 | 绩效面谈、通知偏好、站内公告、委托代理、DMN、多币种、简历解析、开放 API | 否，须先改表 |
| **纯 API / UI 缺失** | 约 15 | 官网职位页、候选人自助、招聘漏斗报表、人力结构分析、多法人报表、批量操作 | 是，模型够用 |
| **依赖外部条件** | 3 | 多轮对话与个性化口径（需 RAG Key）、超时催办（需调度器） | 否，须外部条件 |

这解释了为什么「补页面」能快速推进：15 项属于纯展示层缺口，
而后 11 项无论写多少代码都做不出来。

## 6. 改造优先级建议

按 **（解锁功能数 ÷ 改造成本）** 排序：

| 优先级 | 改造 | 成本 | 解锁 |
|---|---|---|---|
| ~~P0~~ **已完成** | 给 `cert_no_cipher`、`rcu_candidate.email` 加索引 | 极低（2 条 DDL） | 让已做的两个查重功能在大数据量下可用 |
| **P0** | 建 `att_holiday` 表 | 低（1 表 + CRUD） | ATT-F-021 完整、日考勤计算有法定节假日依据 |
| **P1** | 建 `sys_notify_preference`、`flow_ext_delegate`、`cmp_exchange_rate` | 中（各 1 表 + CRUD） | 解锁 PLT-F-004 / FLW-F-009 / CMP-F-023 |
| **P1** | `emp_employee` 加 `cert_no_hash` 并回填 | 中（改表 + 迁移脚本 + 改查重查询） | 加密改造前置；再入职查重长期可靠 |
| **P2** | 建 `emp_contract_term`、`rcu_resume_parse`、`prf_interview` | 中高（涉及解析/审批联动） | EMP-F-014 / RCS-F-007 / PRF-F-008 |
| **P2** | 组织版本扩展到岗位/职级 + 草稿状态机 | 高（改核心模型） | ORG-F-004 完整 |
| **P3** | 人才库独立表、招聘阶段定义表 | 中 | RCS-F-010 / RCS-F-008 的自定义能力 |

**建议先做两个 P0**：加索引是纯收益（无行为变更），建 `att_holiday` 能补齐一个
P0 需求。其余按 P1 顺序推进，每项都需同步 `docs/db/schema-mysql.sql` 并重跑
`init_db.py`（注意该脚本非幂等，只对新库有效）。

## 7. 方法论说明

- **对照基准**取自需求文档的 §3「核心实体」段落与功能点描述中的具体名词
  （如「节假日历」「汇率快照」「面谈记录」），不是凭空推测。
- **表格与实际模型的核对**通过 `information_schema` 查询完成，未依赖文档描述。
- **局限**：本文只判断「有没有承载位置」，不判断「承载得对不对」。
  例如 `emp_lifecycle_case` 用 `payload` JSON 存异动详情，这是有表但语义弱化，
  统计与报表会很别扭——这类问题不在本文范围，需要单独的数据建模评审。

## 8. 本轮已落地的改造（P0 索引）

第 6 节标为 P0 的两条索引已直接落地，因为它们是纯收益、无行为变更。

**改动**（`docs/db/schema-mysql.sql` + 运行库已同步执行）：

```sql
ALTER TABLE emp_employee  ADD INDEX idx_emp_employee_cert  (tenant_id, cert_no_cipher);
ALTER TABLE rcu_candidate ADD INDEX idx_rcu_candidate_email (tenant_id, email);
```

均以 `tenant_id` 为前缀列，与两表既有索引的惯例一致（所有索引都带租户前缀，
因为查询恒带租户隔离条件）。

**验证**（EXPLAIN 实测，非推断）：

| 场景 | type | key | rows |
|---|---|---|---|
| 5000 行下按 email 等值查 | ref | `idx_rcu_candidate_email` | 1 |
| 2 行真实表按 cert_no 查 | ref | `idx_emp_employee_cert` | 1 |

验证时发现一个需要说明的现象：**在只有 1-2 行的真实表上，优化器不一定选新索引**
（所有索引基数都是 1，选哪个都等价）。所以额外造了 5000 行的临时表复验，
确认在真实量级下新索引会被正确选中；临时表已 `DROP`，未污染数据。

如果不做这步复验，会得出「索引建了但没生效」的错误结论——
这也是本文档要强调的：**EXPLAIN 的结论依赖数据量，小表上的执行计划不可信**。
