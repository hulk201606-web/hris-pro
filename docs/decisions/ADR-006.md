# ADR-006: 业务数据层同时支持 MySQL 8.0 与 PostgreSQL 15+

- 状态：Accepted（2026-10-15）
- 决策者：首席架构师 高见远
- 关联 ADR：ADR-001（11 服务拆分）、ADR-003（共享库 + tenant_id + 分片）

## 背景（Background）

原《02 系统架构设计》将数据层锁定为「MySQL 8.0.x 业务主库」。现需求扩展为**同一套业务逻辑与 DDL 基线同时支持 MySQL 8.0 与 PostgreSQL 15+ 两种数据库**，用于满足不同客户部署环境（部分头部客户/政企要求 PG 生态、数据驻留与合规差异），并保持 ShardingSphere-JDBC 分片 + 列级加密能力在两种方言下一致生效。

## 决策（Decision）

1. 采用「**一套逻辑、双份方言 DDL**」策略：业务代码与 MyBatis-Plus Mapper 保持方言中立（不写裸方言 SQL），DDL 按 MySQL / PostgreSQL 分别维护两份基线脚本（`docs/db/schema-mysql.sql` 与 `docs/db/schema-postgresql.sql`）。
2. 关键差异由「方言兼容策略表」逐项收敛（见《12 数据库详细设计》§2）：
   - 主键一律 BIGINT 雪花 ID（应用层生成，含租户位段），彻底规避 MySQL AUTO_INCREMENT 与 PG IDENTITY/SERIAL 差异；
   - 布尔/逻辑删除统一用整数 0/1（MySQL TINYINT / PG SMALLINT），禁用 MySQL BOOLEAN 与 PG boolean 的语义混用；
   - 时间戳统一「存 UTC、无时区」：MySQL DATETIME(3) / PG TIMESTAMP(3)，updated_at 由 MyBatis-Plus MetaObjectHandler 应用层填充（MySQL 不用 ON UPDATE 子句，PG 不用触发器），两侧行为一致；
   - JSON 仅用于 payload/快照/配置类大字段（MySQL JSON / PG JSONB），不做过滤/唯一/排序，需检索的字段提升为标量影子列；
   - 大小写不敏感唯一性：MySQL 依赖 utf8mb4_0900_ai_ci 排序规则天然实现；PG 无 ai_ci 等价物，采用「应用层对标识符类字段（code/username/emp_no 等）写路径统一 trim+lower 规范化 + 对关键登录字段 auth_user.username 建 lower() 函数唯一索引兜底」的策略；
   - upsert 收口到 repository 层方言实现（MySQL `INSERT ... ON DUPLICATE KEY UPDATE` / PG `INSERT ... ON CONFLICT`），service 不写裸 upsert SQL。
3. 迁移工具选 **Liquibase**（一套 changelog 用 `<dbms>` 条件片段区分方言），Flyway 作为备选（按目录 `db/migration/{mysql,postgresql}` 分方言）。
4. ShardingSphere-JDBC 5.4.x+ 继续作为唯一分片/加密层：同一版本同时适配两种方言（见 §后果-验证结论）。

## 后果（Consequences）

### 正面后果

- 客户部署面扩大：MySQL（国内主流）/ PostgreSQL（政企、数据驻留、地理生态）均可交付，不锁定单一供应商。
- 应用层零方言泄漏：Mapper/Service 不感知底层库，未来新增方言（如 openGauss）只增一份 DDL 与 Liquibase 片段。
- 主键/时间/布尔/upsert 等最易踩坑的差异在应用层被显式约定消灭，避免「两库各写一套行为」的历史债务。

### 负面后果（代价）

- **测试矩阵翻倍**：所有涉及数据层的行为（DDL 迁移、分片路由、加密落库、月分区、upsert、分页、事务）需在 MySQL 与 PG 各跑一遍；CI 数据层冒烟用例与集成用例成本接近 2 倍。
- **维护两份 DDL**：字段/索引变更必须双份同步，靠 Liquibase 基线 + 变更集约束，仍需 CodeReview 双文件对照清单，防止漂移。
- **方言边界仍有残留**：JSON 查询、全文检索（PG `tsvector` vs MySQL 全文索引）、分区 DDL 语法、加密列「不可比较/排序/LIKE」约束在两库表述不同，需在 repository 层用少量方言实现或影子列消解，无法做到 100% 一套 SQL。
- **团队技能要求**：DBA/后端需同时熟悉两库的索引、分区、执行计划差异，排障成本上升。

### 验证结论（ShardingSphere 对 PG 支持）

- Apache ShardingSphere 官方明确声明「Multi-DB Support」，5.x 起支持 MySQL / PostgreSQL / SQL Server / Oracle / openGauss 等；5.4.0 Release Notes 明确修复了 PG/openGauss 的加密 like 特性、PG 分区表元数据大小写问题、CDC 对 PG 的支持，说明分片与加密在 PG 上均已收敛到可用状态。
- 结论：ShardingSphere-JDBC 5.4.x+ **同一版本可同时配置 MySQL 与 PG 两种数据源方言**，分片 + 加密插件两库可用；但需遵守其「加密列不支持范围比较 / ORDER BY / LIKE / 计算」的通用限制，检索一律走掩码影子列。
