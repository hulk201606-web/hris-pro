### 1.2 安全维度细节（Bronze）

**已达 Bronze 的部分**：
- JWT HS256 密钥守卫 `JwtSecretGuard.requireStrongSecret()`：拒绝空值 / <32 字节 / 代码库已知默认值，非法即拒绝启动（`hris-common/.../JwtSecretGuard.java`）
- RBAC 垂直越权由后端切面强制：`@RequirePerm` + `PermAspect`，缺失权限抛 20403（`docs/08`）
- 网关丢弃客户端伪造的 `X-User-Id` / `X-Tenant-Id` / `X-User-Roles` / `X-User-Perms`，以 token 为准重写（`JwtAuthGlobalFilter`）
- compose 对 `DB_PASSWORD` / `JWT_SECRET` 用 `:?` 强制校验，缺失即拒绝启动
- 容器非 root 运行（`USER hris`），CI 有 uid != 0 冒烟门禁
- `.gitignore` 排除 `.env`，`.env.example` 强制回纳
- Actuator 仅暴露 `health,info`，未暴露 `env`/`heapdump`/`beans`

**未达 Silver 的部分**：

| 缺口 | 证据 | 风险 |
|------|------|------|
| **真实 DB 口令明文入库** | `scripts/init_db.py:12` `DB_PASSWORD = "<REDACTED>"`，已由 commit `3f811fb` 提交 | 凭据泄露即全库失守；且已进 git 历史，改文件不等于改凭据 |

### 1.3 可观测维度细节（Bronze，本方向核心）

**已达 Bronze 的部分**：
- 11 个服务均引入 `spring-boot-starter-actuator`，`management.endpoint.health.probes.enabled: true`（liveness/readiness 就绪）
- Dockerfile `HEALTHCHECK` 走 `/actuator/health/liveness`，配合 compose `depends_on: service_healthy` 编排启动顺序
- 日志进 docker stdout，`json-file` driver 限 `20m × 3` 轮转
- traceId 已生成并透传（`X-Trace-Id` 在 CORS 允许头列表中）

**未达 Bronze 核心判据的部分**：

| 缺口 | 证据 | 为什么致命 |
|------|------|-----------|
| **无 Prometheus registry** | `grep -rn "micrometer\|prometheus" --include=pom.xml` 零命中；`mvn dependency:list` 显示仅有 `micrometer-core:1.16.5` 与 `spring-boot-micrometer-metrics:4.0.6`，**无任何 registry 实现** | Micrometer 是门面（facade），无 registry 则指标只进内存 `CompositeMeterRegistry`，`/actuator/prometheus` 端点根本不会注册。Bronze 判据「出错看得见」不满足 |
| 指标端点未暴露 | 11 个 `application.yml` 全部 `include: health,info` | 即使加了 registry 也无 `/actuator/prometheus` 可抓 |
| 无 Prometheus / Grafana / Alertmanager 编排 | `find -iname "*prometheus*" -o -iname "*grafana*" -o -iname "*alertmanager*"` 零命中 | 无采集端 |
| 无集中日志采集 | `docs/13 §11` 自陈「缺少集中日志与链路追踪采集（traceId 已有，未接采集端）」 | 12 容器日志需逐个 `docker logs` |
| 无 SLI/SLO 定义 | `docs/09 §4` 描述了 RED 指标诉求，但无机器可判定的 SLO 阈值 | 告警无法量化 |

**Spring Boot 4 版本陷阱（必须注意）**：

Spring Boot 4.0.6 管理 `micrometer.version = 1.16.5`（已从 `spring-boot-dependencies-4.0.6.pom` 核实）。
Boot 4 改用 Prometheus Java client 1.x，registry artifact 是 **`micrometer-registry-prometheus`**，
旧的 `micrometer-registry-prometheus-simpleclient` 在 Boot 4 下**不会注册端点**（返回 404）。
证据：Apache StreamPipes issue #4518 记录了完全相同的现象——升级 Boot 4 后
`/actuator/prometheus` 404，根因是只引入了 `-simpleclient`。
**结论：必须用不带 `-simpleclient` 后缀的 artifact。**

### P0-1 真实数据库口令明文入库

- **影响**：`scripts/init_db.py:12` 的 `DB_PASSWORD = "<REDACTED>"` 已由 commit `3f811fb` 提交进 git。
  任何拿到仓库读权限的人（含 CI 日志、克隆副本、离职交接）都持有该口令。

- **已落地的修复（2026-10-18，代码层）**：

  | # | 动作 | 落点 | 验收 |
  |---|------|------|------|
  | 1 | `init_db.py` 改环境变量注入 | `scripts/init_db.py` | 无 `DB_PASSWORD` 时 stderr 明确报错并 `exit 2` |

  | 11 | 服务数注释纠正 | `docker/build-all.sh:3`、`ci.yml:147,216` | 「12 个」→「11 个」 |

- **仍未完成（需用户决策，见 §4.10）**：**数据库口令轮换**。代码层已不再泄露新口令，
  但历史 commit `3f811fb` 里的旧口令依然有效，**必须轮换才能视为安全**。

#### 关键顺序：先轮换，再清史

```
正确顺序                      错误顺序
  1. 轮换口令  ──────┐          1. 清史 ──────┐
  2. 更新 .env        │          2. 轮换口令   │ ← 此时旧口令
  3. 清史（可选）     │          3. 验证       ┘   仍在 git 历史里
  4. 验证  ←─────────┘
```

**清史不能替代轮换。** 原因：
1. 清史只改写 git 记录，**不改变数据库里的实际口令**——旧口令在库里继续可用。
2. 历史可能已被克隆到多台机器、CI 缓存、第三方镜像、离职同事的本地仓库，
   这些副本不在你的 `filter-repo` 作用域内。
3. 只有轮换能让旧口令**在服务端立即失效**——这是唯一能真正止损的动作。
4. 反过来，轮换后即使清史失败，泄露的也只是**已失效**的旧口令，风险降级为可接受。

**判断是否需要清史**：若该仓库从未推送到任何远端（无 `git remote` 或远端为纯本地），
清史优先级低，轮换即可。若已推送到 GitHub 等远端，则清史 + 轮换都要做，
且清史后需通知所有克隆方重新拉取。

## 3. 监控方案

### 3.0 前置阻断项（必须先做，否则监控落地即引入漏洞）

网关白名单放行 `/actuator/**`，跳过 JWT 校验。指标端点一旦暴露即等于公网可读。
两处必须同步收口：

**收口 1：网关白名单收窄（最小改动，推荐）**

编辑 `hris-gateway/src/main/resources/application.yml`，把第 97 行：

```yaml
      # 放行探针与健康检查；其余 actuator 端点（尤其 prometheus/metrics）必须带 JWT
      - /actuator/health/**
```

**收口 2：指标端点绑定独立管理端口（纵深防御，推荐同时做）**

把 actuator 挪到独立端口，使其在网关路由与业务端口之外。追加到**全部 11 个**
`hris-*/src/main/resources/application.yml` 的 `management:` 块（11 个服务逐个改）：

```yaml
management:
  server:
    # 指标端点独立端口，与业务端口隔离：即便网关误配也打不到 /actuator/prometheus
    port: 9090
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
```

注意：`management.server.port` 生效后，`Dockerfile` 的 `HEALTHCHECK`
（`docker/Dockerfile:96-97`）走 `${SERVER_PORT:-8080}/actuator/health/liveness` 会失效，
必须同步改为 `${MANAGEMENT_PORT:-9090}/actuator/health/liveness`，
并在 `docker-compose.app.yml` 的 `x-app-common.environment` 注入 `MANAGEMENT_PORT: 9090`。
**这是本次改动最大的连带成本，建议先只做收口 1 跑通链路，管理端口列入生产上线前再做。**

**验收命令**：

```bash
# 收口 1 验收：未带 JWT 时 prometheus 端点必须 401/403，而不是 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/actuator/prometheus
# 期望输出：401（未授权）；若输出 200 则收口未生效，立即回滚配置
```

```xml
    <dependencies>
      <!-- Prometheus 指标暴露：Spring Boot 4 使用 Prometheus client 1.x，
           artifact 必须是不带 -simpleclient 后缀的新 registry。
           带 -simpleclient 的旧 registry 在 Boot 4 下不会注册 /actuator/prometheus（返回 404）。
           version 必须省略：由 spring-boot-starter-parent:4.0.6 的 BOM 管理。 -->
      <dependency>
        <groupId>io.micrometer</groupId>
        <artifactId>micrometer-registry-prometheus</artifactId>
      </dependency>
    </dependencies>
```

#### 依赖坐标与版本（查证记录，非推测）

| 项 | 值 | 查证方式 |
|----|----|----------|
| groupId | `io.micrometer` | Maven Central 路径 `io/micrometer/micrometer-registry-prometheus` |
| artifactId | `micrometer-registry-prometheus`（**不带 `-simpleclient`**） | 同上；1.16.5 的 POM 自述：使用 `io.prometheus:prometheus-metrics-core`，若需兼容旧 client 才用 `-simpleclient` |
| version | **1.16.5**（由 BOM 管理，pom 中省略） | 拉取 `spring-boot-dependencies-4.0.6.pom`，读其 `<micrometer.version>` = `1.16.5` |
| 上游 Boot 版本 | `spring-boot-starter-parent:4.0.6` | 项目 `pom.xml` 实际声明 |

三重交叉验证（可复现）：
```bash

  | grep -oP "<micrometer.version>\K[^<]+"
# 输出：1.16.5

# 2) 该坐标 1.16.5 在 Maven Central 真实存在，且用的是新 client
curl -s https://repo1.maven.org/maven2/io/micrometer/micrometer-registry-prometheus/1.16.5/micrometer-registry-prometheus-1.16.5.pom \
  | grep -E "artifactId|description" | head -3
# description 含 "using io.prometheus:prometheus-metrics-core" —— 证实为新 client 1.x

# 3) 项目实际拉取到的版本（加依赖后执行）
mvn -B -ntp -pl hris-auth dependency:list | grep micrometer-registry-prometheus
# 期望：io.micrometer:micrometer-registry-prometheus:jar:1.16.5:compile
```

若不想让 11 个模块各写一遍，更稳妥的做法是：在父 `pom.xml` 的 `<dependencies>` 中声明
（所有模块自动继承），并从各子 `pom.xml` 中移除已有的 `spring-boot-starter-actuator` 声明避免重复。

**注意**：项目当前 `hris-*/pom.xml` 各自持有 `spring-boot-starter-actuator`，
但**没有任何 registry 实现**（实测 `grep -rn "micrometer-registry" --include=pom.xml` 零命中）。
当前依赖树只有 `micrometer-core:1.16.5` + `spring-boot-micrometer-metrics:4.0.6`，
Micrometer 作为门面在没有 registry 时会把指标放进内存 `CompositeMeterRegistry`，
`/actuator/prometheus` 端点不会被注册——这是「加了 actuator 却抓不到指标」的根本原因。

```yaml
# =====================================================================
# 告警规则。阈值口径说明：
#   错误率 5%        —— 运维规范默认阈值
#   p95 > 2s         —— 运维规范默认阈值（较 docs/09 NFR-P-001 的 300ms 宽，
#                       业务侧 NFR 未达标先告警不阻塞，避免告警疲劳）
#   连接池耗尽      —— 立即通知
#   容器消失        —— compose 服务挂掉，兜底信号（当前无编排层采集，用 up==0 近似）
# =====================================================================
groups:
  - name: hris-service-availability
    rules:
      - alert: HrisServiceDown
        expr: up{job="hris-services"} == 0
        for: 1m
        labels:
          severity: P0
        annotations:
          summary: "服务不可达：{{ $labels.service }}"
          description: "实例 {{ $labels.instance }} 已 1 分钟无响应"

      - alert: HrisHighErrorRate
        expr: |
          sum by (service) (
            rate(http_server_requests_seconds_count{job="hris-services", status=~"5.."}[5m])
          )
          /
          sum by (service) (
            rate(http_server_requests_seconds_count{job="hris-services"}[5m])
          ) > 0.05
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "错误率超 5%：{{ $labels.service }}"

      - alert: HrisHighLatencyP95
        expr: |
          histogram_quantile(0.95,
            sum by (service, le) (
              rate(http_server_requests_seconds_bucket{job="hris-services"}[5m])
            )
          ) > 2
        for: 10m
        labels:
          severity: P1
        annotations:
          summary: "p95 延迟 > 2s：{{ $labels.service }}"

  - name: hris-runtime
    rules:
      - alert: HrisJvmHeapPressure
        # Dockerfile 设定 MaxRAMPercentage=70，容器 limit 的 70% 是 JVM 堆上限；
        # 老年代持续超 85% 说明接近 OOMKill
        expr: |
          sum by (service) (
            jvm_memory_used_bytes{area="heap", id="PS-Old-Gen"}
          )
          /
          sum by (service) (
            jvm_memory_max_bytes{area="heap", id="PS-Old-Gen"}
          ) > 0.85
        for: 10m
        labels:
          severity: P1
        annotations:
          summary: "老年代使用率 > 85%：{{ $labels.service }}"

      - alert: HrisHighGcPause
        expr: |
          sum by (service) (
            rate(jvm_gc_pause_seconds_sum{job="hris-services"}[5m])
          ) > 0.2
        for: 10m
        labels:
          severity: P2
        annotations:
          summary: "GC 停顿占比偏高：{{ $labels.service }}"

  - name: hris-middleware
    rules:
      - alert: MysqlConnectionsHigh
        expr: mysql_global_status_threads_connected{job="mysql"} / mysql_global_variables_max_connections > 0.8
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "MySQL 连接数超 max_connections 的 80%"

      - alert: MysqlDown
        expr: up{job="mysql"} == 0
        for: 1m
        labels:
          severity: P0
        annotations:
          summary: "mysqld-exporter 无法采集 MySQL"

      - alert: HostDiskSpaceLow
        expr: |
          node_filesystem_avail_bytes{job="node", fstype!="tmpfs", mountpoint="/"}
          /
          node_filesystem_size_bytes{job="node", fstype!="tmpfs", mountpoint="/"}
          < 0.15
        for: 5m
        labels:
          severity: P1
        annotations:
```

### 4.1 备份范围决策：白名单，不用前缀过滤

**实例实况（2026-10-18 实测）**：MySQL 实例上有 **12 个库、172 张表**。

| 类别 | 库 | 表数 | 处理方式 |
|------|----|------|---------|
| 本项目业务库（10 个） | `att_db`(16) / `auth_db`(9) / `cmp_db`(12) / `emp_db`(11) / `flow_db`(51) / `org_db`(9) / `plt_db`(11) / `prf_db`(16) / `rag_db`(13) / `rcu_db`(11) | 159 | **纳入备份** |
| 非本项目遗留库（2 个） | `yunjian`(13) / `yunjian_verify`(13)，表前缀 `sn_*`（sn_note / sn_attachment / sn_audit_log …）+ `flyway_schema_history` | 26 | **明确排除** |

遗留库判定依据（已实测确认）：
- 全仓 grep `yunjian|sn_note|sn_attachment|sn_audit` 在 `*.java` / `*.yml` / `*.xml` / `*.sql` / `*.ts` / `*.vue` 中**零命中**
- 库名与表前缀（`sn_*`）与本项目 `hris_` 模块命名体系无任何交集
- 判定为另一个项目在本机 MySQL 上的残留

#### 为什么用显式白名单，不用 `hris_` 前缀过滤

**结论：必须用显式白名单，前缀过滤在此项目上会静默备份 0 个库。**

实测证据：
```bash
cd /d/GC_Workspace/hris-pro
# 本项目的库名里带 hris_ 前缀的数量
grep -oiP "CREATE DATABASE( IF NOT EXISTS)? \`?\Khris_[a-z_0-9]+" docs/db/schema-mysql.sql | wc -l
# 输出：0
# 全仓是否存在任何 hris_xxx_db 形式的库名引用
grep -rn "hris_[a-z]*_db" --include="*.sql" --include="*.java" --include="*.yml" .
# 输出：空
```

原因：项目模块名叫 `hris-auth`，但**库名是 `auth_db` 而非 `hris_auth_db`**
（`docs/db/schema-mysql.sql` 与 `docker-compose.app.yml` 逐服务注入的 `DB_URL` 均为 `xxx_db` 形式）。
`hris_` 是**模块前缀**不是**库前缀**。若用 `WHERE schema_name LIKE 'hris\_%'` 过滤，
结果是空集——备份脚本会「成功」退出并产出一个只含系统库的空归档，
而校验环节若只看「文件非空 + 含 MySQL dump 头」就会**全部通过**，属最危险的静默失效。

四条方案对比：

| 方案 | 覆盖 10 库 | 排除遗留库 | 新增库自动纳入 | 评价 |
|------|------------|------------|----------------|------|
| `--all-databases` | 是 | **否**（会拖进 yunjian） | 是 | 边界污染，不符要求 |
| `LIKE 'hris_%'` 前缀过滤 | **否（0 个）** | 是 | 否 | **静默备份空集，禁止使用** |
| `LIKE '%\_db'` 后缀过滤 | 是（10 个） | 是 | 是 | 可用，但会误纳未来任何 `*_db` 遗留库；且把命名约定当契约，耦合 |
| **显式白名单（推荐）** | 是 | 是 | 否，需手工加 | **边界显式可审计，新增库时漏加会被下面的校验拦住** |

选定**显式白名单**，理由：
1. 备份边界是安全边界，必须显式可读、可评审、可审计，不能靠命名约定隐式推导
2. 新增库时白名单不会自动纳入——这是**特性不是缺陷**：它强制人在新增库时想一次「这个库要不要备份」，
   而 `LIKE '%\_db'` 会让新库在无人察觉的情况下进入或退出备份范围
3. 白名单与 `docs/db/schema-mysql.sql` 的 `CREATE DATABASE` 列表一一对应，可做交叉校验（见下方脚本第 5 步）

**新增库漏加的兜底**：脚本内置「schema 与白名单一致性」检查，
若 `schema-mysql.sql` 里出现白名单未覆盖的业务库，脚本**报错退出**而非静默通过。

**遗留库处置建议（需 owner 决策，非运维单方面决定）**：
本方案只做「备份排除」，**不建议擅自删除**——`yunjian` 13 张表可能是他人项目的数据，
删库是不可逆操作。建议：(a) 确认无归属后备份一份归档留档；(b) 与 owner 确认后清理；
(c) 若确认长期不用，用 `RENAME DATABASE`（MySQL 8.0 支持）或改权限隔离，
比直接 `DROP` 安全。**在 owner 确认前，运维侧只做排除，不做删除。**

### 4.2 MySQL 备份脚本（`scripts/backup-mysql.sh`）

```bash
#!/usr/bin/env bash
# =====================================================================
# hris-pro MySQL 备份脚本（10 个业务库白名单，单文件归档）
#
# 用法：
#   bash scripts/backup-mysql.sh            # 每日备份（保留 7 天 + 周备 28 天）
#   RETENTION_DAYS=14 bash scripts/backup-mysql.sh   # 自定义日备保留天数
#   BACKUP_DIR=/data/backups/mysql bash scripts/backup-mysql.sh
#
# 设计要点：
#   1. 用容器内自带的 mysqldump（与 mysql:8.0 服务端同版本，杜绝版本错配）
#   2. 显式白名单逐库 dump，不用 --all-databases（会拖入非本项目的 yunjian 遗留库）
#      也不用 LIKE 'hris_%' 前缀过滤（本项目库名是 auth_db 而非 hris_auth_db，
#      前缀过滤会静默备份 0 个库，见 §4.1）
#   3. --single-transaction 保证 InnoDB 一致性快照，不锁表（在线可跑）
#   4. --routines --triggers --events 必须带：Flowable 依赖触发器，缺了恢复不出流程引擎
#   5. 落盘后立即校验非空、含 MySQL dump 头、且 10 个业务库全部在位
#   6. gzip -1：备份在凌晨跑，压缩比收益远小于耗时收益
#   7. 备份前做「schema 与白名单一致性」检查，新增库漏加时报错退出而非静默通过
# =====================================================================
set -euo pipefail

BACKUP_ROOT="${BACKUP_DIR:-/data/backups/mysql}"
RETENTION_DAYS="${RETENTION_DAYS:-7}"
WEEKLY_RETENTION_DAYS="${WEEKLY_RETENTION_DAYS:-28}"
MYSQL_CONTAINER="${MYSQL_CONTAINER:-hris-mysql}"
MYSQL_USER="${DB_USERNAME:-root}"
TIMESTAMP="$(date +%Y%m%d_%H%M%S)"
DAY_OF_WEEK="$(date +%u)"

# ---------- 业务库白名单（10 个） ----------
# 依据：docs/db/schema-mysql.sql 的 CREATE DATABASE 列表 + docker-compose.app.yml 逐服务 DB_URL
# 明确排除：yunjian / yunjian_verify（非本项目遗留，全仓代码零引用，表前缀 sn_*）
HRIS_DATABASES=(
  att_db auth_db cmp_db emp_db flow_db
  org_db plt_db prf_db rag_db rcu_db
)

# ---------- 口令从环境读，绝不在命令行明文出现（ps 可见） ----------
: "${DB_PASSWORD:?DB_PASSWORD 未设置，退出。请 export DB_PASSWORD=<口令>}"

DAILY_DIR="${BACKUP_ROOT}/daily"
WEEKLY_DIR="${BACKUP_ROOT}/weekly"
mkdir -p "$DAILY_DIR" "$WEEKLY_DIR"

STAGE="$(mktemp -d)"
trap 'rm -rf "$STAGE"' EXIT

echo "[$(date '+%F %T')] 开始备份（容器=${MYSQL_CONTAINER}，业务库 ${#HRIS_DATABASES[@]} 个）"

# ---------- 步骤 1：白名单与实例实际库做双向核对 ----------
# 目的：白名单里的库不存在 = 环境异常；实例里的业务库不在白名单 = 新增库漏加。
# 两种情况都必须显式失败，不能静默继续（否则备份缺库却显示成功）。
HOST_DB_LIST="$(docker exec -e MYSQL_PWD="$DB_PASSWORD" "$MYSQL_CONTAINER" \
  mysql -uroot -N -B -e "SHOW DATABASES;" | tr -d '\r')"

missing=()
for db in "${HRIS_DATABASES[@]}"; do
  if ! grep -qx "$db" <<< "$HOST_DB_LIST"; then
    missing+=("$db")
  fi
done
if [ ${#missing[@]} -gt 0 ]; then
  echo "[FAIL] 白名单中的库在实例上不存在：${missing[*]}"
  echo "       请确认 DB_URL_HOST 是否指向了正确的 MySQL 实例"
  exit 1
fi

# 反向检查：实例上形如 *_db 的库是否都在白名单内（yunjian / yunjian_verify 不匹配后缀，天然被排除）
# 用 comm 而非 grep -vxF "${ARRAY[@]}"：数组展开后会被 grep 当成「文件名」而非 pattern，
# 产生 "No such file or directory" 噪声且结果不可信（此坑已实测踩过）。
EXTRA_DBS="$(comm -23 \
  <(grep -E '_db$' <<< "$HOST_DB_LIST" | sort -u) \
  <(printf '%s\n' "${HRIS_DATABASES[@]}" | sort -u) || true)"
if [ -n "$EXTRA_DBS" ]; then
  echo "[WARN] 实例上存在未纳入白名单的 *_db 库（本次已排除，需确认是否为新增业务库）："
  tr '\n' ' ' <<< "$EXTRA_DBS"
  echo ""
fi

# ---------- 步骤 2：逐库 dump 后合并 ----------
# 不用 --all-databases：会连带备份 yunjian / yunjian_verify，污染恢复边界
: > "$STAGE/hris_all.sql"
for db in "${HRIS_DATABASES[@]}"; do
  echo "  -> dump ${db}"
  # 用 MYSQL_PWD 传口令，避免 -p"$DB_PASSWORD" 出现在容器进程列表
  docker exec -e MYSQL_PWD="$DB_PASSWORD" "$MYSQL_CONTAINER" \
    mysqldump \
      --databases "$db" \
      --single-transaction \
      --quick \
      --routines \
      --triggers \
      --events \
      --default-character-set=utf8mb4 \
      --hex-blob \
      --set-gtid-purged=OFF \
      --column-statistics=0 \
      >> "$STAGE/hris_all.sql"
done

SIZE_BYTES=$(stat -c%s "$STAGE/hris_all.sql")
if [ "$SIZE_BYTES" -lt 10240 ]; then
  echo "[FAIL] 备份文件仅 ${SIZE_BYTES} 字节，明显异常（<10KB），中止以免覆盖有效备份"
  exit 1
fi

gzip -1 -c "$STAGE/hris_all.sql" > "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz"

# 周备：每周一单独留一份，保留期更长（应对「误删发生在日备之后」的场景）
if [ "$DAY_OF_WEEK" = "1" ]; then
  cp "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz" "${WEEKLY_DIR}/hris_all_${TIMESTAMP}.sql.gz"
  echo "  -> 已生成周备"
fi

# ---------- 步骤 3：完整性校验 ----------
# 校验 gzip 合法性
if ! gunzip -t "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz" 2>/dev/null; then
  echo "[FAIL] gzip 完整性校验失败，删除损坏文件"
  rm -f "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz"
  exit 1
fi
# 校验 MySQL dump 头
if ! gunzip -c "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz" | head -5 | grep -q "MySQL dump"; then
  echo "[FAIL] 文件头不是 MySQL dump 格式，疑似备份内容异常"
  exit 1
fi

# ---------- 步骤 4：业务库逐个点名（防漏库，这是最关键的一条校验） ----------
DUMPED_DBS="$(gunzip -c "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz" \
  | grep -oP "^CREATE DATABASE \`?\K[a-z_0-9]+" | sort -u)"
absent=()
for db in "${HRIS_DATABASES[@]}"; do
  grep -qx "$db" <<< "$DUMPED_DBS" || absent+=("$db")
done
if [ ${#absent[@]} -gt 0 ]; then
  echo "[FAIL] 备份中缺失业务库：${absent[*]}，删除该备份文件"
  rm -f "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz"
  exit 1
fi

# 反向确认遗留库确实没被拖进来
if grep -qxE 'yunjian|yunjian_verify' <<< "$DUMPED_DBS"; then
  echo "[FAIL] 备份中混入了非本项目遗留库，边界被污染，删除该备份文件"
  rm -f "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz"
  exit 1
fi

echo "  -> 校验通过：10 个业务库全部在位，遗留库未混入"

echo "  -> ${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz ($(du -h "${DAILY_DIR}/hris_all_${TIMESTAMP}.sql.gz" | cut -f1))"

# 清理过期备份
find "$DAILY_DIR"  -name 'hris_all_*.sql.gz' -type f -mtime +$RETENTION_DAYS       -delete
find "$WEEKLY_DIR" -name 'hris_all_*.sql.gz' -type f -mtime +$WEEKLY_RETENTION_DAYS -delete

echo "[$(date '+%F %T')] 备份完成"
```

### 4.3 Flowable 引擎表（`flow_db` 51 张表的多数）是否需要备份

**结论：必须备份，且不能排除。排除引擎表是本方案里最容易犯且后果最严重的错误。**

`flow_db` 共 51 张表，其中业务扩展表仅 6 张（`flow_ext_model` / `flow_ext_biz_relation` /
`flow_ext_node_form` / `flow_ext_task_action` / `flow_ext_event_outbox` / `flow_ext_timeout_cfg`），
其余 45 张为 Flowable 引擎表。按「只备业务表、排除引擎表」看似能缩小备份体积，
但会导致恢复后流程引擎完全不可用。

引擎表按前缀分三类，风险逐类升高：

| 前缀 | 含义 | 排除后的后果 | 严重度 |
|------|------|--------------|--------|
| `ACT_GE_*` | 通用资源：流程定义/模型/表单元数据 | 流程模型全丢，等价于没部署过流程；所有 flow_ext_model 变成悬空引用 | **致命** |
| `ACT_RU_*` | 运行时：进行中的流程实例、任务、变量 | **在途审批全部丢失**——员工正在走的请假/报销流程实例与待办消失，业务中断且无法追溯 | **致命** |
| `ACT_HI_*` | 历史：已完成流程的审计记录 | 审批历史丢失，**合规审计链断裂**（`docs/08` 安全与多租户设计要求操作可审计） | **致命** |

判断依据（四条）：

1. **「Flowable 有自己的历史表」不等于「Flowable 自己会备份历史表」**。
   `ACT_HI_*` 只是引擎写进 MySQL 的普通表，Flowable **没有独立的备份机制**，
   它完全依赖数据库层的备份。排除 `ACT_HI_*` 不会让 Flowable 帮你留档，只会让你丢数据。

2. **在途实例（`ACT_RU_*`）是业务连续性载体，不是可重算的派生数据**。
   `ACT_RU_TASK` 里是「谁在等谁审批」，无法从任何其他数据推导重建。

3. **`docs/08` 的审计要求绑定在历史表上**。审批留痕是 HR 域合规刚需，
   而 `ACT_HI_*` 正是留痕的物理载体。排除它等于把合规风险从「备份不全」升级为「无法举证」。

4. **体积收益微乎其微，恢复风险收益巨大**。引擎表多为空表或小表（流程定义、变量、ID 序列），
   真正占体积的是 `ACT_HI_*` 的历史行，而那恰恰是最该备份的部分。
   为省几 MB 丢掉在途审批与审计链，是典型的错误权衡。

**因此本方案的 `flow_db` 采用整库 dump，不做任何表级排除。**
若后续 `flow_db` 因历史累积导致体积过大（参考 `docs/09 §5`：业务库约 80GB 热数据），
正确做法是按保留期归档 `ACT_HI_*`（引擎原生支持历史级别配置与历史清理任务），
**而不是在备份时排除引擎表**——前者是生命周期管理，后者是数据丢失。

### 4.4 恢复演练（每季度 1 次，必须实际执行）

**演练必须在隔离环境进行**，禁止在生产库上验证：

```bash
# ========== 步骤 0：生成一次性演练口令 ==========
# 用变量承载，理由有二：
#   1) 不在文档/脚本里留任何口令字面量，凭据门禁（check-secret.js）才能真正绿；
#   2) 避免 mysql -p<明文> 出现在容器进程列表里（ps 可见）。
# 口令随机生成，用完即弃；容器 rm 后无任何残留，无需备份也无需清史。
RESTORE_PW="$(openssl rand -base64 24 | tr -d '/+=' | head -c 24)"
echo "演练口令已生成（不打印明文）"

# ========== 步骤 1：起隔离实例（独立容器名与端口，不碰生产数据卷） ==========
docker run -d --name hris-restore-test \
  -e MYSQL_ROOT_PASSWORD="$RESTORE_PW" \
  -p 13306:3306 \
  --network hris-pro_hris-net \
  mysql:8.0

# 等就绪（最多等 120s）
for i in $(seq 1 60); do
  if docker exec hris-restore-test mysqladmin ping -uroot -p"$RESTORE_PW" --silent 2>/dev/null; then
    echo "实例就绪（第 ${i}0 秒）"; break
  fi
  sleep 2
done

# ========== 步骤 2：灌入最近一次备份 ==========
LATEST=$(ls -t /data/backups/mysql/daily/hris_all_*.sql.gz | head -1)
echo "使用备份：$LATEST"
gunzip -c "$LATEST" | docker exec -i hris-restore-test \
  mysql -uroot -p"$RESTORE_PW" --default-character-set=utf8mb4
# 期望：静默完成，无 ERROR

# ========== 步骤 3：结构完整性 ==========
# 3.1 10 个业务库都在
docker exec hris-restore-test mysql -uroot -p"$RESTORE_PW" -N -e "SHOW DATABASES;" \
  | grep -cE '^(auth|org|emp|flow|plt|att|rcu|cmp|prf|rag)_db$'
# 期望：10

# 3.2 遗留库未被恢复（本方案的备份边界只含 10 个业务库）
docker exec hris-restore-test mysql -uroot -p"$RESTORE_PW" -N -e "SHOW DATABASES;" \
  | grep -cE '^(yunjian|yunjian_verify)$'
# 期望：0。返回 > 0 说明备份被污染，需追查备份脚本是否误用 --all-databases。
# 说明：这是「预期结果」而非「缺陷」——遗留库不属于本项目恢复范围。
# 若需单独恢复遗留库，那是另一个项目的备份流程，不在本方案内。

# 3.3 表数量级与线上一致（参照线上实况：业务库 159 张 + flow 引擎表）
docker exec hris-restore-test mysql -uroot -p"$RESTORE_PW" -N -e "
  SELECT table_schema, COUNT(*) FROM information_schema.tables
  WHERE table_schema NOT IN ('mysql','information_schema','performance_schema','sys')
  GROUP BY table_schema ORDER BY table_schema;"
# 逐库比对线上实况：att(16)/auth(9)/cmp(12)/emp(11)/flow(51)/org(9)/plt(11)/prf(16)/rag(13)/rcu(11)
# 合计 159 张；偏差 > 1% 即判演练失败

# 3.4 Flowable 引擎表在（流程引擎能不能起来的关键，参见 §4.3）
docker exec hris-restore-test mysql -uroot -p"$RESTORE_PW" -N -e "
  SELECT COUNT(*) FROM information_schema.tables
  WHERE table_schema='flow_db' AND table_name LIKE 'ACT_%';"
# 期望 > 0（线上实况为 45 张）。若为 0，说明备份时漏了 flow_db 或漏了 --routines/--triggers。

  SELECT
    SUM(table_name LIKE 'ACT_GE_%') AS ge_resources,
    SUM(table_name LIKE 'ACT_RU_%') AS ru_runtime,
    SUM(table_name LIKE 'ACT_HI_%') AS hi_history
  FROM information_schema.tables WHERE table_schema='flow_db';"
# 三者均须 > 0。GE=流程定义 RU=在途实例 HI=审计历史，任一为 0 都判演练失败

# ========== 步骤 4：应用能连上恢复库（真实可用性验证） ==========
# 用恢复实例的 13306 端口拉起 hris-auth 做冒烟
# 判据：日志无 SQLSyntaxError / DatabaseNotFound，且 /actuator/health/liveness 返回 200
docker exec hris-restore-test mysql -uroot -p"$RESTORE_PW" -N -e "
  SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='auth_db';"
# 期望：9（线上实况）

# ========== 步骤 5：清理 ==========
docker rm -f hris-restore-test
```

### 4.5 DDL 快照的定位纠偏

`docs/db/schema-mysql.sql` 是**全量 DDL 快照**，不是备份。四个必须知道的事实：

1. **不含 Flowable 引擎表**：该文件 114 张表全为业务逻辑表，
   `flow_db` 只有 6 张 `flow_ext_*`。`ACT_RU_TASK` / `ACT_HI_PROCINST` 等由 Flowable 运行时自建。
   用 `schema-mysql.sql` 恢复会得到一个**跑不了流程引擎的 flow_db**。
2. **与线上实况存在表数差**：DDL 快照 114 张 vs 线上 159 张业务表，
   差额来自 Flowable 引擎表与运行时演进，进一步说明快照不可替代实况备份。
3. **不含种子数据**：`scripts/seed_auth_admin_rbac.sql` 才是 RBAC/管理员初始数据来源。
   新库部署需 `schema-mysql.sql` + `seed_auth_admin_rbac.sql` + Flowable 自建表，三步齐全才算等价。
4. **不是幂等脚本（2026-10-18 实测确认）**：
   ```bash
   grep -ci "CREATE DATABASE IF NOT EXISTS" docs/db/schema-mysql.sql   # 10
   grep -ci "CREATE TABLE IF NOT EXISTS"  docs/db/schema-mysql.sql   # 0
   grep -ci "CREATE TABLE"                docs/db/schema-mysql.sql   # 114
   ```
   **10 个 `CREATE DATABASE` 全部带 `IF NOT EXISTS`，但 114 个 `CREATE TABLE` 一个都没带。**
   因此对已初始化的库重复执行会以 MySQL 错误码 **1050（Table already exists）** 中断。

   **对备份论述的影响**（这是本条与 §4 的直接关联）：
   - `init_db.py` 原 docstring 与 README 都写「幂等」，**该表述不准确**，已更正为「仅用于首次建库」。
   - **建空环境与恢复生产是两条完全不同的路径**，不可混用：
     | 场景 | 手段 | 幂等性 | 能恢复 Flowable 引擎表？ |
     |------|------|--------|--------------------------|
     | 建空环境（本地起库） | `schema-mysql.sql` + `seed_auth_admin_rbac.sql` | **否**，重复执行报 1050 | 否（需引擎自建） |
     | 恢复生产 | `mysqldump` 实况备份（§4.2） | 是（`--single-transaction` 快照） | **是** |
   - 推论：**恢复演练必须用备份，不能用 schema 文件**。若误用 schema 恢复生产库，
     既得不到 Flowable 引擎表，又会因表已存在而中途失败——这是最容易犯的误操作。

结论：schema 文件用于「建空环境」（且仅一次），备份用于「恢复生产」（可重复）。两者不可互相替代。

### 4.6 Nacos 配置备份（用导出 API，不用卷备份）

**为什么不用卷备份**：`nacos-data` 是 Derby 内嵌库的目录，
直接 tar 卷属于「用文件系统的手段备份一个数据库」，版本一升级格式变就废。
用官方导出 API 得到的是可跨版本、可读、可 diff 的配置文本。

```bash
#!/usr/bin/env bash
# =====================================================================
# Nacos 配置导出备份
# 前提：compose 中 NACOS_AUTH_ENABLE=false（docker-compose.yml:20），
#       故导出接口无需 token。若后续开启鉴权，需先取 accessToken 并加 -H 头。
# =====================================================================
set -euo pipefail

BACKUP_ROOT="${BACKUP_DIR:-/data/backups/nacos}"
TIMESTAMP="$(date +%Y%m%d_%H%M%S)"
NACOS_ADDR="${NACOS_ADDR:-127.0.0.1:8848}"
OUT="${BACKUP_ROOT}/nacos_config_${TIMESTAMP}.json"
mkdir -p "$BACKUP_ROOT"

curl -sS --max-time 30 -X POST \
  "http://${NACOS_ADDR}/nacos/v1/cs/configs?export=true&tenant=${NACOS_NAMESPACE:-}" \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data '' \
  -o "$OUT"

if [ ! -s "$OUT" ]; then
  echo "[FAIL] Nacos 导出为空，接口可能不可达或格式变更：$OUT"
  exit 1
fi

# 保留期 30 天：配置变更频率低但影响面大，比数据备份留更久
find "$BACKUP_ROOT" -name 'nacos_config_*.json' -type f -mtime +30 -delete
echo "[$(date '+%F %T')] Nacos 配置已导出：$OUT ($(du -h "$OUT" | cut -f1))"
```

**验收命令**：

```bash
# 导出文件非空且能被解析为 JSON
LATEST=$(ls -t /data/backups/nacos/nacos_config_*.json | head -1)
test -s "$LATEST" && python -c "import json,sys; json.load(open(sys.argv[1])); print('JSON OK')" "$LATEST"
```

**恢复**：

```bash
curl -sS -X POST "http://127.0.0.1:8848/nacos/v1/cs/configs?import=true" \
  -F "file=@${LATEST}" 
```

> **重要前提**：当前 Nacos 配置几乎为空（`infra/` 下只有 `rocketmq/broker.conf`，
> 各服务配置全在各自 `application.yml` 里，靠环境变量注入）。
> 因此 Nacos 备份的实际价值是**为将来配置外置留好兜底**，而非保护现有资产。
> 真正的配置资产保护应由 §3.0 之外的一项补充来做：把 `.env.example` 纳入版本控制并锁版本
> （当前已做到），生产 `.env` 另存密钥管理系统。

### 4.7 Milvus / MinIO 备份

```bash
#!/usr/bin/env bash
# =====================================================================
# Milvus 向量数据卷冷备 + MinIO 对象存储导出
# 前置：仅 rag / storage profile 启动时才有这两个容器，未启动则跳过（不算失败）
# =====================================================================
set -euo pipefail

BACKUP_ROOT="${BACKUP_DIR:-/data/backups}"
TIMESTAMP="$(date +%Y%m%d_%H%M%S)"

# ---------- Milvus：卷级冷备 ----------
# 依据：docker-compose.yml:173-186，standalone + ETCD_USE_EMBED + local storage，
#      全部状态在 milvus-data 单卷内。停止容器后打包，避免写入不一致。
if docker ps --format '{{.Names}}' | grep -q '^hris-milvus$'; then
  echo "[$(date '+%F %T')] Milvus 在线，先停容器保证一致性"
  docker stop hris-milvus
  mkdir -p "${BACKUP_ROOT}/milvus"
  docker run --rm \
    -v hris-pro_milvus-data:/data:ro \
    -v "${BACKUP_ROOT}/milvus":/backup \
    alpine:3.20 \
    tar czf "/backup/milvus_${TIMESTAMP}.tar.gz" -C /data .
  docker start hris-milvus
  find "${BACKUP_ROOT}/milvus" -name 'milvus_*.tar.gz' -mtime +7 -delete
  echo "  -> Milvus 备份完成"
else
  echo "[SKIP] hris-milvus 未运行（rag profile 未启用），跳过"
fi

# ---------- MinIO：附件 / 简历（合规留存 ≥ 2-3 年，不可只备 7 天） ----------
if docker ps --format '{{.Names}}' | grep -q '^hris-minio$'; then
  echo "[$(date '+%F %T')] MinIO 在运行，用 mc mirror 导出到宿主"
  mkdir -p "${BACKUP_ROOT}/minio"
  # 注意：minio/minio 官方镜像已迁出 Docker Hub（见 docker-compose.yml:170 注释），
  # 故 mc 用 quay.io 镜像，避免同样的拉取失败问题
  docker run --rm \
    --network hris-pro_hris-net \
    -v "${BACKUP_ROOT}/minio":/backup \
    quay.io/minio/mc:latest \
    mirror --overwrite --quiet \
    "hris-minio/hris" /backup
  find "${BACKUP_ROOT}/minio" -type f -mtime +30 -delete
  echo "  -> MinIO 备份完成"
else
  echo "[SKIP] hris-minio 未运行（storage profile 未启用），跳过"
fi
```

**恢复演练要点**：
- Milvus：停容器 → 解包覆盖卷 → 起容器 → 用 `hris-rag` 的索引重建接口验证向量可检索
- MinIO：`mc mirror --remove` 回灌（**注意加 `--remove` 前先确认备份完整**，否则会删源数据）

```bash
# tar 包可解压且含关键文件
```

### 4.8 Redis：明确不备份（决策记录）

`docker-compose.yml:117` 为 `redis-server --appendonly yes`，数据落 `redis-data` 卷。
**决策：不做备份。** 理由：

- Redis 在本项目中承载缓存 / 分布式锁 / 限流 / refreshToken（`docs/13 §11` 列为待迁目标）
- 这些数据全部**可从 MySQL 重建或可重新签发**，无唯一性数据
- 备份 AOF 反而会引入「恢复出陈旧锁 / 陈旧限流计数」的风险，比不备份更危险

**但有前提**：若 refreshToken 迁到 Redis（§1.2 的 Silver 阻塞项），
则**必须**改为迁 Redis 的同时明确「登出态可丢失」，并把黑名单改为带 TTL 的相对过期设计，
否则重启后所有用户被强制登出。迁移方案须与该决策一并评审。

## 4A. 数据库口令轮换方案（待用户拍板）

> 代码层已不再硬编码任何口令（见 §2 P0-1 表格第 1-11 项）。
> 但历史 commit `3f811fb` 中的旧口令仍然有效，**必须轮换才能视为安全**。
> 轮换会影响数据访问，决策权在用户。本节为可直接执行的方案，**运维不代为执行**。

### 4A.1 决策要点（供用户判断）

| 问题 | 影响 | 建议 |
|------|------|------|
| 是否存在生产环境数据库？ | 生产库轮换需停机窗口 | 仅本机联调库 → 随时可做；生产库 → 需维护窗口 |

| 是否需要保持兼容旧口令？ | **不建议** | 若有外部系统用旧口令，应改为各自独立账号 |

### 4A.2 轮换步骤（可直接执行）

> **本节已于 2026-10-18 由 team-lead 执行完毕并实测通过**：
> 旧口令失效（MySQL 1045）、新口令登录成功、12 个业务库完整。
> **实测纠正**：本机 MySQL **只有 `root@localhost` 一个账号，没有 `root@`%``**。
> 原方案假设存在 `'root'@'%'`（容器场景常见），在本机不成立。
> 若将来改为容器化 MySQL 或需要远程连接，才需要额外创建 `'root'@'%'` 账号。
> 下方步骤保留完整形态供参考，实际执行时按步骤 2 的查询结果为准。

```bash
# ---------- 步骤 1：生成新口令（不打印到终端，避免进 shell history） ----------
# 用 openssl 生成 32 字节随机串，写入文件而非回显
umask 077
NEW_PW="$(openssl rand -base64 48 | tr -d '\n/+=' | head -c 32)"
echo "$NEW_PW" > /tmp/hri_new_pw.txt
echo "新口令已生成并暂存 /tmp/hri_new_pw.txt（权限 600），未回显"

# ---------- 步骤 2：确认当前账号与认证方式（重要，避免改错账号） ----------
mysql -uroot -p -e "SELECT user, host, plugin FROM mysql.user WHERE user='root';"
# 看清楚：host 有 % 还是 localhost？plugin 是 mysql_native_password 还是 caching_sha2_password？
# mysql:8.0 默认 caching_sha2_password，部分老客户端需注意兼容性
# 本机实测：仅 root@localhost 一条，无 root@%

# ---------- 步骤 3：改密（把 <新口令> 换成步骤 1 生成的值） ----------
# 注意：ALTER USER 是原子操作，成功即生效；本机实测还需 FLUSH PRIVILEGES 才完全生效
mysql -uroot -p -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '<新口令>'; FLUSH PRIVILEGES;"
# 若步骤 2 显示 root 有多个 host（如 'root'@'%'），需逐个改
mysql -uroot -p -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '<新口令>';"

# ---------- 步骤 4：立即验证新口令可用、旧口令失效 ----------
# 用 --defaults-extra-file 传凭据，避免命令行出现 -p<明文>（ps 可见）
{
  echo '[client]'
  echo 'user=root'
  echo "password=$(cat /tmp/hri_new_pw.txt)"
} > /tmp/hri_client.cnf
chmod 600 /tmp/hri_client.cnf
mysql --defaults-extra-file=/tmp/hri_client.cnf -e "SELECT 'new-pw-ok' AS result;"
# 旧口令应失败（这才是轮换生效的证据）
# OLD_PW 由操作者从密码管理器取出后注入：read -rs OLD_PW && export OLD_PW
: "${OLD_PW:?请先 export OLD_PW（轮换前的口令，从密码管理器取）}"
MYSQL_PWD="$OLD_PW" mysql -uroot -e "SELECT 1;" 2>&1 | grep -q "denied" \
  && echo "[OK] 旧口令已失效" || echo "[FAIL] 旧口令仍可用，轮换未生效"

# ---------- 步骤 5：清暂存文件 ----------
shred -u /tmp/hri_new_pw.txt 2>/dev/null || rm -f /tmp/hri_new_pw.txt
```

**若本机没有可用的 mysql client**（当前环境实测：`command -v mysql` 无输出），
用容器内的 client 执行，同样安全：

```bash
NEW_PW="$(openssl rand -base64 48 | tr -d '\n/+=' | head -c 32)"

# 改密。host 段按步骤 2 的查询结果填：本机实测为 'localhost'（无 '%'）
docker exec -e MYSQL_PWD="$OLD_PW" hris-mysql \
  mysql -uroot -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '$NEW_PW'; FLUSH PRIVILEGES;"

# 验证：换新口令应能连
docker exec -e MYSQL_PWD="$NEW_PW" hris-mysql mysql -uroot -e "SELECT 'ok';" && echo "新口令可用"
# 验证：旧口令应被拒（OLD_PW 由操作者从密码管理器取，不写进命令历史）
docker exec -e MYSQL_PWD="$OLD_PW" hris-mysql mysql -uroot -e "SELECT 1;" 2>&1 | grep -q denied \
  && echo "[OK] 旧口令已失效"
unset NEW_PW

# 把新口令写入 .env（DB_PASSWORD= 那一行）
# 用 sed 精确替换，避免手工编辑时把口令留在编辑器历史里
sed -i "s|^DB_PASSWORD=.*|DB_PASSWORD=$(openssl rand -base64 48 | tr -d '\n/+=' | head -c 32)|" .env
echo "已更新 .env 的 DB_PASSWORD"
```

**注意**：若 MySQL 由 compose 容器提供（`--profile db`），还须确认
`docker-compose.yml` 的 `MYSQL_ROOT_PASSWORD` 是变量注入（已于 §2 第 6 项改为
`${DB_PASSWORD:?...}`），因此**改 `.env` 即同时改容器口令**，两者不会脱节。

```bash
# 有输出 = 已推送 → 轮换 + 清史都要做
```

**清史步骤（仅在已推送时执行）**：

```bash
# 强烈建议先备份当前仓库（清史不可逆，出错无法回退）

git filter-repo --path scripts/init_db.py --invert-paths --force
# 若只想替换内容而非删整个文件，用 --replace-text 更精准：
# 用 printf 生成替换规则，口令由 shell 变量传入，文档与仓库里不留明文。
# 前置：read -rs OLD_PW && export OLD_PW   （从密码管理器取轮换前的口令）

printf '%s==>***REMOVED***\n' "$OLD_PW" > ../replacements.txt
git filter-repo --replace-text ../replacements.txt --force

# 必须强推（rewritten history 无法 fast-forward）
git push --force --mirror

# 通知所有克隆方重新拉取（或各自执行相同清理命令）
```

**清史后的收尾**：
1. 通知所有克隆方（同事 / CI / 自己的其他机器）重新 clone 或执行
   `git reflog expire --expire=now --all && git gc --prune=now`
2. 检查远端是否有 fork / PR 快照（GitHub 上 fork 会保留旧对象，需站内支持清理）
3. 检查 CI 缓存、构建产物中是否残留旧文件

> **再次强调**：清史是「让旧口令不再出现在版本库里」，轮换是「让旧口令在服务端失效」。
> **只有轮换能真正止损**，清史是减少暴露面。顺序不可颠倒。

## 4B. git 历史清理方案（用户已拍板：立即轮换 + 清史）

> 前置：口令轮换已由 team-lead 执行完毕并实测（旧口令 1045 失效、新口令可用、12 库完整）。
> 本节只处理**版本库历史**。再次强调：**清史不能替代轮换**，轮换已完成是清史可行的前提。

### 4B.1 关键事实（决定方案复杂度）

实测 `git log --oneline --all` 与 `git ls-remote origin`：

| 项 | 实测值 | 含义 |
|----|--------|------|
| 本地提交数 | **6 个**（不是 3 个） | `fa59e30` → `fa1eba4` → `71d4783` → `01e1c0a` → `3f811fb` → `9132126` |
| 远端 `origin/main` | **`01e1c0a`** | **早于泄露提交 `3f811fb`** |
| 本地 `main` 相对远端 | `ahead 2` | `3f811fb`（泄露）与 `9132126` 都只在本地 |
| 远端是否含 `scripts/init_db.py` | **否**（`git ls-tree origin/main` 无此文件） | **明文口令从未推到远端** |
| 本地备份分支 | `backup-before-scrub` 指向 `3f811fb` | **注意：这会保留泄露提交，需一并处理** |

**结论：泄露内容目前只在本地 git 历史中，远端是干净的。** 这大幅降低了清理风险——
无需 `git push --force`，也不可能影响其他协作者。

### 4B.2 方案选型：`reset --soft` vs `filter-repo`

| 方案 | 适用性 | 判定 |
|------|--------|------|
| `git reset --soft` + 重建提交 | **本例最佳**。只有 2 个本地提交需重写，且两个提交都要保留 message 与内容 | **推荐** |
| `git filter-repo --replace-text` | 面向「历史很大 / 泄露点很多 / 需保留全部提交结构」的批量清理 |  overkill，且会改写全部 6 个提交的 hash |
| `git filter-branch` | 已废弃、慢、易出错（官方文档明确不推荐新项目使用） | **不采用** |

选 `reset --soft` 的理由：
1. 泄露提交及其后**仅 2 个**，重写成本可忽略。
2. `3f811fb` 与 `9132126` 的业务内容本身没问题（只有 `init_db.py` 一行口令要改），
   **应该保留 message、作者、变更内容**，只把那一行改掉。
3. `filter-repo` 会连带改写前 4 个无关提交的 hash，凭空增加远端不一致风险（虽然远端没这几个提交）。
4. 远端无需 force push，**不会影响任何协作者**。

## 5. K8s 编排是否值得现在做

### 结论：**暂不做。** 现在做 K8s 是错配投入，收益远低于成本。

### 5.1 理由（基于实测事实，非泛论）

**成本侧（反对现在做）**：

| 项 | 实测依据 |
|----|----------|
| 当前无任何 K8s 资产 | `find -iname "*k8s*" -o -iname "*kube*"` 零命中，从零起步 |
| K8s 无法替代仍需补齐的基建 | 备份、监控告警、DDL 版本化**与编排形态无关**。做 K8s 不会让备份脚本出现，也不会让 Prometheus 采到数据 |
| 会引入两套编排双轨维护 | 现有 compose 已通过 CI `config` 门禁（`ci.yml:186-194`）且验证可运行；并行的 Helm 清单意味着每次改动要改两处 |
| K8s 要求 DB 迁移工具先行 | 当前无 Flyway/Liquibase（实测零命中），K8s 滚动更新 + 无版本化 DDL = 升级时 schema 错配，比 compose 更危险 |
| 依赖已存在的编排层采集 | Prometheus 采 K8s 需 kube-state-metrics / prometheus-operator，当前一个都没有 |

**收益侧（为什么现在确实不需要）**：

| K8s 能力 | 当前是否需要 | 依据 |
|----------|--------------|------|
| 副本数 + HPA 弹性 | **不需要** | `docs/09 §3` 的 HPA 前提是「无状态服务水平」，但当前 refreshToken 在 JVM 内存（`docs/13 §11`），**多副本即登出**，扩不出副本。先做 K8s 是本末倒置 |
| 蓝绿 / 金丝雀 | **不需要** | 当前单一租户试点流量，`docs/09 NFR-A-005` 的金丝雀需求对应的是规模化后的发布风险 |
| 自愈 / 滚动更新 | compose `restart: unless-stopped` + `service_healthy` 依赖已覆盖基本场景 | 11 服务单机，节点级故障用不上 |
| 服务网格 | **不需要** | 网关已做 JWT 验签 + 限流 + 伪造头清洗，Sentinel 端点限流已实现 |

**决定性论据**：K8s 的价值密度与「服务数 × 副本数 × 节点数」正相关。
当前形态是 **11 服务 × 1 副本 × 1 节点 = 11 个 Pod**，
这是 K8s 收益曲线的起点（低于它，K8s 只带来运维开销）。
按 `development-costs.md` 的隐性成本模型，「运维监控/日志/告警/备份」本就是必须计入的项——
先把这部分做扎实，比换编排形态的边际收益高得多。

### 5.2 触发条件（满足任一即启动 K8s 迁移）

**必须全满（硬门槛）**：

1. **refreshToken 已迁 Redis**（否则多副本必然故障，HPA 无意义）
2. **refreshToken 已迁 Redis**（否则多副本必然故障，HPA 无意义）
3. **数据库迁移工具已落地**（Flyway 或 Liquibase，`V*__*.sql` 版本化脚本在库）
4. **DDL 已完成 expand-contract 改造**，且已演练过向前兼容
5. **容器镜像已推送至镜像仓库**（当前 `build-all.sh` 只打本地 tag，无 `push`，`ci.yml` 中 `push: false`）

**满足任一（触发信号）**：

- 需上 **≥ 2 台**应用节点（单机故障即业务中断，compose 无解）
- 单服务需 **≥ 3 副本**以支撑 5,000 TPS 打卡洪峰（`docs/09 NFR-P-001` NFR-P-003）
- 服务数 **≥ 25**（compose 启动编排与依赖排期开始失控）
- 需**跨可用区容灾**以满足 `docs/09 NFR-A-002` 的「K8s 双 AZ」
- 需**自动扩缩容**以应对峰谷（人力成本 / 云成本优化诉求）

### 5.3 若启动，最小可用 K8s 清单（现在不实施，供后续直接取用）

以下为**触发条件满足后**的最小起步集，共 6 类对象：

| # | 对象 | 数量 | 要点 |
|---|------|------|------|
| 1 | `Deployment` | 11 | 每个服务 1 个；镜像 `hris/<svc>:<version>`；`imagePullSecrets` 走私有仓库 |
| 2 | `Service` | 11 | ClusterIP；端口统一 8080（沿用容器内收敛约定）；`app` label 选择器 |
| 3 | `Ingress` | 1 | 网关 8080 暴露；TLS 证书走 cert-manager（对齐运维规范「SSL/TLS 已配置」） |
| 4 | `ConfigMap` | 2 | 非敏感配置（Nacos 地址、Redis 地址）；**密钥不走 ConfigMap** |
| 5 | `Secret` | 2 | `JWT_SECRET` / `DB_PASSWORD`，`type: Opaque`，base64；生产用 External Secrets 或 Sealed Secrets |
| 6 | `HPA` | 11（可延后） | CPU 70%（与 `MaxRAMPercentage=70` 呼应）；打卡洪峰可按 `RocketMQ` 堆积量做自定义指标 HPA（`docs/09 §3` 已提出该设想） |

**再加 3 项生产必配**（不进 Silver 起步集）：

- **探针**：`livenessProbe` → `/actuator/health/liveness`；`readinessProbe` → `/actuator/health/readiness`
  （`management.endpoint.health.probes.enabled: true` 已就绪，无需改代码）
- **资源**：`requests`/`limits` 必填。当前 compose **完全没有 `deploy.resources`**，
  `MaxRAMPercentage=70` 在无 limit 时会按宿主机内存的 70% 计算堆，
  这是个隐性 OOM 风险（详见 §7 风险登记）
- **`PodDisruptionBudget`**：生产 SLA 要求核心链路 99.95%（`docs/09 NFR-A-001`），需 PDB 保证驱逐期可用性

## 6. 分步实施计划（按投入产出比排序）

原则：**先堵安全窟窿，再补可观测，再建兜底，最后碰编排**。
每步给出机器可判定的验收命令，验收不过则停在该步。

### 第 1 步：轮换数据库口令并清除入库凭据（0.5 人日，最高优先级）

**为什么第一**：这是唯一一个「已经在流血」的问题。其余缺口都是「将来会出事」，这个是「已经出事」。

动作：
1. 轮换生产库口令

## 7. 风险登记（本轮评估发现但不在上述 6 步内）

| # | 风险 | 影响 | 建议时点 |
|---|------|------|----------|
| R1 | compose **无 `deploy.resources`**，`MaxRAMPercentage=70` 在无 limit 时按宿主机内存计算堆 | 宿主机内存被单服务吃满，OOMKill 风险不可控 | **生产上线前必做**（给每个服务加 `mem_limit`） |
| R2 | `APP_VERSION` 默认 `latest`（可变标签） | 回滚时无法确定「上一个版本」的准确 digest | **生产上线前必做**（强制显式版本号） |
| ~~R3~~ | `broker.conf` 中 `brokerIP1=127.0.0.1`（`infra/rocketmq/broker.conf`） | 容器内 broker 注册 127.0.0.1，消费端拉不到 topic 路由 | **已修复**（2026-10-18）：改为 `brokerIP1=rocketmq-broker`（compose 服务名，hris-net 上可解析） |
| R4 | `infra/rocketmq/broker.conf;D` 是一个误建的目录 | 残留垃圾，`.gitignore` 未覆盖 | 低优先，随时清理 |
| ~~R5~~ | `docker/build-all.sh:3` 与 `ci.yml:147,216` 注释写「12 个」，实际 `ALL_SERVICES` 为 11 项 | 文档与代码口径不一致，误导后续维护者 | **已修复**（2026-10-18）：改为「11 个（hris-common 为共享库不产镜像）」 |
| R6 | `internal-path-marker` 配置声明但无实现（§1.2） | 注释承诺的安全语义不存在 | 随第 1 步一并处置：要么实现，要么删配置与注释 |
| R7 | MinIO 备份保留 30 天不满足 `docs/09 §6` 的 2 年合规要求 | 附件数据恢复窗口远小于留存要求 | 生产上线前必做（改对象存储版本化 + 跨区） |
| R8 | 敏感字段（身份证/银行卡/手机号）明文存储 | 合规风险 | 生产上线前必做（KMS 信封加密） |
