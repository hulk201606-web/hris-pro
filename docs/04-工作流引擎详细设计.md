# 04 工作流引擎详细设计（Flowable 集成）

> 服务：hris-flow　引擎：Flowable 7.2.x（BPMN+DMN）　决策依据：ADR-002（独立流程中台）

## 1. 集成架构

```
业务服务(employee/att/rcs/cmp/prf/org)
   │ ①Feign: POST /flow/instances (bizType,bizKey,initData,tenantId)
   ▼
hris-flow
 ├─ 扩展层: ModelService / FormBindService / BizRelationService / AssigneeResolver / TimeoutJob
 ├─ 引擎层: ProcessEngine(CMMN 不启用) + DMN DecisionEngine + 事件监听器
 └─ flow_db: ACT_* 引擎表 + flow_ext_* 扩展表
   │ ②事件: hris-flow-task-created / completed / rejected / timeout / instance-finished
   ▼
RocketMQ ──► 各业务服务消费回写单据状态（幂等: flowEventId）
        └──► platform 通知 / 待办推送
```

- 引擎表与业务表物理分库（flow_db 独立 MySQL 实例/schema），杜绝跨域数据耦合。
- 多租户：Flowable 原生 `tenant` 字段（值 = 平台 tenantId），所有 RepositoryRuntimeService/TaskService
  查询强制带 `tenantId(...)`；网关层保证 tenantId 只来自 JWT，不可由 body 伪造。

## 2. 扩展表设计（flow_ext_*）

| 表 | 关键字段 | 用途 |
|---|---|---|
| flow_ext_biz_relation | id, tenant_id, proc_inst_id, biz_type, biz_key, status | 业务单据 ↔ 流程实例映射，发起幂等锁（uk: tenant+biz_type+biz_key） |
| flow_ext_model | id, tenant_id, proc_def_key, version, bpmn_xml, form_schema_json, deploy_state | 模型草稿/部署记录（引擎 ACT_RE_* 之外保存设计态） |
| flow_ext_node_form | proc_def_id, node_id, form_schema_json, readonly_expr | 节点级表单绑定（字段权限表达式） |
| flow_ext_task_action | id, task_id, action, operator, comment, attachments, delegate_from, ts | 审批动作明细（意见/附件/委托链） |
| flow_ext_event_outbox | event_id, topic, payload, state, retry_cnt | 事件出站表（事务消息兜底，重试+死信告警） |
| flow_ext_timeout_cfg | proc_def_id, node_id, remind_cron, escalate_after_h, escalate_to | 节点超时催办/升级配置 |

## 3. 核心时序（以请假为例）

```
员工提交(ATT) → att 校验额度冻结 → POST /flow/instances(ATT_LEAVE, bizKey=请假单id,
  days/类型/薪酬敏感无关变量)
→ flow: DMN 决策表(请假审批路由.dmn: days≤3→直属上级; ≤7→+部门负责人; >7→+分管)
→ UserTask 创建 → 监听器 → outbox → MQ task-created → platform 通知审批人
→ 审批人同意(带意见/附件) → 网关判断 → 结束 → instance-finished(agree)
→ att 消费: 置单通过、写考勤日历、额度正式扣减（幂等）
→ 若驳回: att 解冻额度、单据回"可修改重提"
```

## 4. 审批人解析（AssigneeResolver）

优先级链：`指定人 > 岗位角色(数据范围过滤) > 直属上级(EMP 汇报线) > 部门负责人(ORG-F-019) >
HRBP > 表达式(自研 EL 子集)`。解析发生在任务创建时（动态），非流程变量预写；候选组+认领模式支持团队池。
解析失败（如汇报线缺失）兜底：挂"待指派"队列并通知 HR 管理员（FLW-F-015），不阻塞不丢单。

## 5. 任务操作语义约束

| 操作 | 语义 | 约束 |
|---|---|---|
| 驳回 | 三策略：终止回发起人/退上一节点/退指定节点 | 指定节点仅管理员配的流程支持跳回 |
| 加签 | 前加签（先问再办）/后加签/并行加签 | 加签链完整记录于 task_action.delegate_from |
| 转办 | 任务所有权转移 | 原审批人保留可见，委托≠免责（留痕） |
| 撤回 | 发起人撤回 | 仅当无已处理节点时允许 |
| 超时 | 提醒→催办→升级改派→自动通过/驳回(按配置) | 自动处理仅限低风险模板（补卡），薪酬类禁止 |

## 6. 表单设计

- 动态表单 JSON Schema（字段/校验/联动），节点级只读/必填表达式。
- 表单数据存业务服务（唯一事实源），flow 只缓存提交快照（渲染轨迹用）；
  **敏感字段（薪酬数字）默认脱敏快照**，审批页经业务 API 实时取数（CMP-F-019 密域）。

## 7. 一致性与对账

- 发起：业务先落单（状态=发起中）再调 flow，失败重试（幂等键），终以 MQ 事件收敛。
- 对账任务（PLT-F-011 调度）：扫描 flow_ext_biz_relation 与业务单状态漂移 > 5min 的记录，告警+自动补偿。
- 引擎历史清理：已结束实例 18 个月后归档导出（06 归档策略），运行库保持精瘦。

## 8. 兼容性风险与降级预案（关键）

Flowable 7.2.x 官方基于 Spring Boot 3.x 验证（7.0 起支持 Boot 3 / jakarta 命名空间）。本项目基线 Boot 4.0.x，
**实现第一阶段必须做引擎装配验证**，验证清单：
1. `flowable-spring-boot-starter-process` 在 Boot 4 的自动配置是否可用（`@ConditionalOn...` 元数据兼容）；
2. Jackson 2→3 迁移对 Flowable 序列化（变量持久化 JPA/ObjectMapper）的影响；
3. 事务管理器与 Spring 6.2/7 的 `@Transactional` 语义兼容。

降级预案（按优先级）：
- A. 不用 starter，自建 `@Configuration` 手工装配 ProcessEngineConfigurationImpl（starter 仅是自动配置壳，引擎核心不依赖 Boot）。
- B. 锁 hris-flow 单服务用 Boot 3.5.x（其余服务 Boot 4.0.x）——微服务异构框架版本可接受但需文档明示。
- C. 推动升级到 Flowable 对 Boot 4 的适配版（发布后回填版本矩阵）。

## 9. 测试要点（设计阶段预留）

- 模板回归：17 条预置流程各配 1 条黄金用例（正常/驳回/超时升级三分支）。
- 并发：同一 bizKey 重复发起、任务同时被认领/转办的乐观锁竞争。
- 租户隔离渗透：跨 tenantId 查询/操作任务必须 403（见 08 测试矩阵）。
