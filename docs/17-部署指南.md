# 智云 HR 部署指南（容器化）

> 适用范围：`hris-pro` 12 个模块（11 个微服务 + 网关 + 公共库）的容器化构建与编排。
> 前置依赖已在 `docker-compose.yml`（中间件）中定义，本文档只覆盖**应用层**。
> 本地脚本联调方式（`scripts/run-one.sh`）仍适用于开发阶段，见 §6。

---

## 1. 架构速览

```
                    ┌──────────────┐
   浏览器 ─────────► │   gateway    │ :8080  （唯一对外入口）
                    └──────┬───────┘
             hris-net 内服务发现（Nacos :8848）
        ┌──────┬──────┬──┴───┬──────┬──────┬──────┐
     auth  org  emp  flow  plat  att   rcu   cmp  prf  rag
     :8080 （容器内统一端口，由 Nacos 注册到宿主机 8101..8110 或经网关访问）
        └──────┴──────┴──────┴──────┴──────┴──────┘
              ↓ MySQL（各服务独立库）/ Redis / RocketMQ / Milvus
```

**关键设计**：容器内所有服务统一监听 `8080`（靠 Nacos 注册的实例端口区分），
宿主机侧端口仅对网关暴露；微服务如需直连调试，在 compose 中按需追加 `ports` 映射。

## 2. 快速开始

```bash
# ① 准备环境变量（必填 DB_PASSWORD / JWT_SECRET）
cp .env.example .env
openssl rand -base64 48      # 生成 JWT_SECRET（≥32 字节）填入 .env

# ② 构建全部 12 个镜像
bash docker/build-all.sh
# 或指定版本：APP_VERSION=1.0.0 bash docker/build-all.sh

# ③ 拉起中间件（首次）
docker compose up -d                    # Nacos + RocketMQ + Redis
docker compose --profile db up -d       # 如使用容器内 MySQL
docker compose --profile rag up -d      # 如需要 ES + Milvus

# ④ 初始化数据库（首次，幂等）
python scripts/init_db.py

# ⑤ 同步权限点（首次，扫描 @RequirePerm 幂等写入）
DB_PASSWORD=<你的密码> python scripts/seed_rbac_from_source.py

# ⑥ 拉起应用
docker compose -f docker-compose.yml -f docker-compose.app.yml up -d

# ⑦ 查看状态与日志
docker compose -f docker-compose.yml -f docker-compose.app.yml ps
docker compose -f docker-compose.yml -f docker-compose.app.yml logs -f gateway
```

访问网关：`http://localhost:8080`，前端开发服务器 `http://localhost:5173`。

## 3. 环境变量契约

所有密钥经 `.env` 注入，**仓库内不硬编码**（`JwtSecretGuard` 启动即校验，
弱密钥或缺失会直接启动失败）。模板见 `.env.example`。

| 变量 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `DB_PASSWORD` | 是 | — | 数据库密码 |
| `JWT_SECRET` | 是 | — | JWT 签名密钥，**≥32 字节**，各服务必须一致（网关与 auth 同源验签） |
| `DB_URL_HOST` | 否 | `mysql` | JDBC 主机；用外部 MySQL 时改为实际地址 |
| `DB_URL_PORT` | 否 | `3306` | JDBC 端口 |
| `DB_USERNAME` | 否 | `root` | 数据库用户 |
| `APP_VERSION` | 否 | `latest` | 镜像 tag（`docker/build-all.sh` 与 compose 共用） |
| `CORS_ORIGIN` | 否 | `http://localhost:5173` | 网关允许的前端来源，**换端口必须同步放开** |
| `PORT_GATEWAY` | 否 | `8080` | 网关宿主机端口 |
| `DASHSCOPE_API_KEY` | 否 | 空 | 留空时 RAG 降级为占位向量（索引重建仍可用） |
| `MILVUS_HOST` / `MILVUS_PORT` | 否 | `milvus` / `19530` | 向量库地址 |

> **数据库连接串说明**：各服务 `application.yml` 只识别**整体 `DB_URL`** 变量，
> 不做 `DB_HOST`/`DB_NAME` 拼装，因此 compose 为每个服务注入完整 JDBC URL，
> 由 `.env` 的 `DB_URL_HOST`/`DB_URL_PORT` 拼出各服务对应的库地址。

## 4. 镜像构建

### 4.1 参数化 Dockerfile（`docker/Dockerfile`）

一个 Dockerfile 构建全部 12 个模块，通过 `--build-arg MODULE=hris-xxx` 区分：

```bash
docker build -f docker/Dockerfile --build-arg MODULE=hris-auth -t hris/auth:1.0.0 .
```

**为什么参数化而非每服务一个 Dockerfile**：
12 份文件会造成配置漂移（基础镜像版本、JVM 参数、非 root 用户策略各不一致），
参数化后这些关注点只有一份定义。

设计要点：

| 阶段 | 内容 |
|------|------|
| builder | `maven:3.9-eclipse-temurin-21`，先 `dependency:go-offline` 预热依赖层，再 `package -pl <MODULE> -am` |
| runtime | `eclipse-temurin:21-jre-jammy`，只带 JRE + fat jar，无编译工具链 |
| 依赖缓存 | pom 层与源码层分离，业务代码变更不会失效依赖层 |
| 非 root | 容器内建 `hris` 系统用户，`USER hris` 运行 |
| 健康检查 | `HEALTHCHECK` 走 Actuator `liveness`，配合 compose `depends_on` 编排 |
| JVM | `MaxRAMPercentage=70` + G1，**不硬编码 `-Xmx`**（避免超出容器 limit 被 OOMKill） |
| 时区 | 固定 `Asia/Shanghai` |

### 4.2 批量构建

```bash
bash docker/build-all.sh                 # 全部 12 个
bash docker/build-all.sh gateway rag     # 只构建指定服务（跳过其余）
```

各服务共享 builder 层缓存，第 2 个及以后的镜像通常只需增量编译时间。

## 5. CI（`.github/workflows/ci.yml`）

5 个 job，**最快失败优先**：

| job | 内容 | 触发时机 |
|-----|------|----------|
| `gates` | emoji 扫描、硬编码颜色扫描、**单文件 ≤300 行**门禁 | 与后端并行，秒级反馈 |
| `backend` | Flowable × Boot 4 装配门禁 → `scripts/test-all.sh`（73 用例）→ 打包 jar 上传 artifact | 独立 |
| `frontend` | `npm ci` → `vue-tsc` type-check → 生产构建 → 上传 dist | 独立 |
| `docker` | 构建 gateway + rag 镜像（非 root/jar 完整性冒烟）→ compose 语法校验 | 依赖 backend |
| `all-passed` | 汇总门禁（任一失败则整体失败） | 依赖全部 |

**为什么只构建 2 个镜像**：全量 12 个镜像构建约 20+ 分钟，
CI 只验证 Dockerfile 正确性（gateway 覆盖通用路径，rag 覆盖唯一含 Spring AI +
Milvus SDK 的重依赖路径），全量构建交给 `docker/build-all.sh` 在发布流水线执行。

**镜像冒烟检查**（CI 内实际断言）：

- 容器内 `id -u` 不为 `0`（强制非 root）
- `/app/app.jar` 大小 > 1MB（防止未正确打包的镜像通过）

## 6. 与本地脚本方式的关系

| 场景 | 方式 | 说明 |
|------|------|------|
| **开发调试** | `scripts/run-one.sh <模块> <端口> <库>` | 前台常驻 + 精确日志，改代码热重启快 |
| **联调验证** | `scripts/start-all.sh` | 注意：Agent/沙箱场景下其 nohup 子进程会随任务结束被回收，须逐个后台任务拉起 |
| **集成测试** | `scripts/test-all.sh [--e2e]` | `--e2e` 需 `DB_PASSWORD` 环境变量（不提供默认值） |
| **部署/演示** | 本文档的 compose 方式 | 隔离性好、可整体重建、不受进程回收影响 |

## 7. 常见问题

**Q: `docker compose config` 报 `required variable DB_PASSWORD is missing`**
A: 未创建 `.env`。执行 `cp .env.example .env` 并填入必填项。这是有意设计——缺密钥时
立即失败，而不是用弱默认值启动。

**Q: `depends on undefined service "mysql"`**
A: `mysql` 在 `db` profile 中。compose 的 `app.yml` 已用 `required: false` 声明为可选依赖，
若仍报错说明 compose 版本过旧（需 Compose v2.20+）。

**Q: 服务启动报 `Client not connected, current status:STARTING`**
A: Nacos 未就绪。compose 的 `depends_on: nacos: service_healthy` 已处理；
若 Nacos 容器异常，检查 `docker compose logs nacos`。

**Q: 前端登录 403（curl 正常）**
A: 网关 CORS 未放开该前端端口。设置 `CORS_ORIGIN=http://localhost:<你的端口>`
后重启网关。curl 不带 `Origin` 头，所以不会复现此问题。

**Q: `docker build` 拉取基础镜像 502 Bad Gateway**
A: Docker Hub 网络问题。使用镜像加速：`docker pull dockerproxy.net/library/<image>`
后 `docker tag` 回原名，或在 Docker Desktop 配置 registry mirror。

**Q: Milvus 连接失败（RAG）**
A: 未启动 `rag` profile：`docker compose --profile rag up -d`。
另注意 RAG 无 API Key 时会降级为占位向量，这是预期行为（见 `docs/15` §14）。

## 9. 备份与恢复

设计依据与完整论证见 `docs/18-生产化基线评估与实施计划.md` 第 4 节（MySQL 白名单
逐库备份、Nacos 导出 API、Milvus/MinIO 冷备与镜像导出、systemd timer、恢复演练
通过标准）。本节只写操作入口。

### 9.1 备份脚本

| 脚本 | 备份对象 | 方式 | 保留期 |
|------|----------|------|--------|
| `scripts/backup-mysql.sh` | 10 个业务库（白名单逐库 dump） | 容器内 mysqldump + gzip，产物落 `BACKUP_DIR/mysql/daily|weekly` | 日备 7 天 + 周备 28 天 |
| `scripts/backup-nacos.sh` | Nacos 全部配置 | 官方导出 API | 30 天 |
| `scripts/backup-milvus-minio.sh` | Milvus 向量卷 / MinIO 对象 | 停容器卷级冷备 / mc mirror | Milvus 7 天 / MinIO 30 天 |
| `scripts/backup-all.sh` | 以上全部（顺序执行） | systemd 入口，任一失败整体退出非 0 | - |

手工执行示例（口令一律环境变量注入，不写入任何文件）：

```bash
export DB_PASSWORD='<生产库口令>'
BACKUP_DIR=/data/backups bash scripts/backup-all.sh          # 全量
MYSQL_CONTAINER=hris-mysql bash scripts/backup-mysql.sh      # 仅 MySQL
```

容器未启用时（rag / storage profile 未启动）Milvus、MinIO 分支输出 SKIP 并以 0
退出，不算失败；MySQL 缺库、多库（`*_db` 不在白名单）、备份内容异常时显式失败。

### 9.2 systemd 定时备份（生产推荐）

模板在 `deploy/systemd/`（`hris-backup.service` / `hris-backup.timer` /
`backup.env.example`），安装三步（详见 service 文件头注释）：

```bash
# 1. 拷贝单元文件
cp deploy/systemd/hris-backup.service deploy/systemd/hris-backup.timer /etc/systemd/system/

# 2. 建口令文件（只填变量名对应值，绝不入库入 git），权限必须 600
mkdir -p /etc/hris-pro
cp deploy/systemd/backup.env.example /etc/hris-pro/backup.env
vi /etc/hris-pro/backup.env          # 填 DB_PASSWORD 等
chmod 600 /etc/hris-pro/backup.env && chown root:root /etc/hris-pro/backup.env

# 3. 启用
systemctl daemon-reload
systemctl enable --now hris-backup.timer
```

验收：`systemctl list-timers hris-backup.timer --no-pager` 可见下次触发时间
（每日 03:10 + 随机打散 600s）；`systemctl start hris-backup.service` 后
`journalctl -u hris-backup.service -n 50 --no-pager` 应看到三个步骤全部 OK。
systemd 依赖非 0 退出码告警，不要用 `|| true` 之类的方式吞掉失败。

### 9.3 恢复演练（每季度至少一次，必须实跑）

`scripts/restore-drill.sh` 在隔离容器（独立端口 13306，不碰生产数据卷）灌入最近
一次日备并自动执行 docs/18 §4.4 的全部通过标准：10 库在位、遗留库为 0、各库表数
与线上偏差不超过 1%、flow_db 的 act_ge_/act_ru_/act_hi_ 三类引擎表均大于 0；
追加 `SMOKE=1` 时还会用恢复实例拉起 hris-auth 验证服务可用。演练口令随机生成、
不打印、容器删除后无残留。

```bash
BACKUP_DIR=/data/backups bash scripts/restore-drill.sh            # 结构校验
BACKUP_DIR=/data/backups SMOKE=1 JWT_SECRET='<32字节以上>' \
  bash scripts/restore-drill.sh                                   # 含服务冒烟
```

演练结束自动清理容器；失败时可加 `KEEP_CONTAINER=1` 保留现场排查。全流程耗时
会打印在案，用于校准 docs/09 的 RTO 指标。

### 9.4 恢复（真实事故）

```bash
gunzip -c /data/backups/mysql/daily/<最新备份>.sql.gz | \
  docker exec -i hris-mysql mysql -uroot --default-character-set=utf8mb4
```

Nacos 恢复：`curl -X POST "http://127.0.0.1:8848/nacos/v1/cs/configs?import=true"
-F "file=@<最新导出>.json"`。Milvus/MinIO 恢复要点见 docs/18 §4.7（MinIO 回灌
加 `--remove` 前必须先确认备份完整）。注意：恢复生产必须用实况备份，不能用
`docs/db/schema-mysql.sql`（它不含 Flowable 引擎表且非幂等，见 docs/18 §4.5）。
