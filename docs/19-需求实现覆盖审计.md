## 2. 两个必须指出的结构性缺口

### 2.1 四个模块有完整后端但无任何前端管理界面

| 模块 | API 端点数 | 数据表 | 前端管理页 |
|---|---|---|---|
| 组织管理 ORG | 16 | 9 | **0** |
| 员工管理 EMP | 10 | 11 | **0** |
| 平台支撑 PLT | 16 | 11 | **0** |
| 流程中心 FLW | 15 | 6 | **0** |

管理端菜单注册表（`frontend/src/router/admin-menu.ts`）只登记了 rcu / att / cmp / prf / kb 五个模块。org 与 emp 的 P0 需求合计 24 项、后端实现完整，但 HR 管理员目前**无法通过界面**维护组织架构与员工档案，只能走 API。

这是"功能满足度"与"可用性"之间的最大落差：接口层达标，操作层缺失。

### 2.2 知识库智能问答只有索引能力，没有问答入口

`hris-rag` 的 22 个端点全部是知识空间 / 文档 / 切片 / 标签 / 评测集的 CRUD，加上一个 `POST /kb/index/rebuild`。**没有 `/qa` 或 `/chat` 端点**。

对应需求 KBD-F-008（智能问答，P0）、KBD-F-011（无召回拒答，P0）均无法判定为已实现。原因是 RAG 阶段 C 依赖 DashScope API Key，当前环境无 Key，语义检索链路（真实 embedding + 检索 + 生成）未打通——索引与向量写入已验证可用，问答闭环未闭环。

## 5. 方法论与局限

**判定依据（四类证据，缺一即降级）**
1. API 端点：契约 `docs/openapi.gen.json` 中是否存在对应 path + method
2. 数据表：`docs/db/schema-mysql.sql` 中是否存在承载该能力的表与关键字段
3. 业务逻辑：Service 层是否存在对应方法与守卫（如状态机、编制校验、密域权限）
4. 前端可用性：`frontend/src/views/` 与管理端菜单注册表是否存在入口

**局限（必须说明）**
- **静态审计，未做功能实测**。例如"算薪引擎"判定为已实现，依据是 `payroll-preview` 端点 + `PayrollPreviewService` 取数逻辑存在，但未验证计算结果与考勤/社保取数的正确性。
- **"部分实现"含主观判断**。如 ORG-F-004 判定为部分，依据是缺"草稿版本"状态机；若产品侧认为"生效日期 + 快照"已足够，则应计为已实现。
- **跨模块实现未重复计数**。ORG-F-016（数据权限范围定义）在 `hris-auth` 的 `AuthDataScope` 实现，计为已实现；EMP-F-025（敏感字段脱敏）同理。

## 6. 若要把完成度提上去，优先级建议

1. **补 4 个模块的管理界面**（ORG / EMP 优先）。后端已就绪，前端是纯增量工作，对"可用"的提升最大。
2. **打通 RAG 问答闭环**（拿到 DashScope Key 后），解锁 KBD-F-008 / F-009 / F-010 / F-011 四项 P0/P1。
3. **P0 的 4 项完全缺失**（FLW-F-019 模板、PLT-F-011 调度、SELF-F-005 工资条页、KBD-F-011 拒答）逐项评估：调度中心可先用现有轮询替代，模板与工资条页成本低。
4. **P1 的 27 项未实现**按期排入下一阶段，其中 CMP-F-017（多法人合并报表）、PLT-F-005/F-006（报表中心）依赖只读聚合库，属架构级工作量。

## 7. 后续修复进展（审计后的执行记录）

本节记录审计结论落地情况，原 §1-§6 的审计结论保留不改，以保持可追溯。

### 7.1 已修复：一期模块的权限校验缺口（安全）

审计时未列此项，是在动手补页面时发现的——`PermAspect` 只拦截标注了
`@RequirePerm` 的方法（`@Around("@annotation(requirePerm)")`），无注解的端点
完全不做权限校验。而当时全仓 302 个 `@RequirePerm` 中，二期（代码生成）占 290 个，
一期手写模块合计仅 12 个。

后果：任何持有效 JWT 的用户都能创建法人主体、删除岗位、改编制配额、审批他人单据、
改系统字典——网关只验签，不做垂直越权拦截。

| 模块 | 修复前 | 修复后 | 新增 |
|---|---|---|---|
| hris-org | 2 | 27 | 25 |
| hris-employee | 4 | 13 | 9 |
| hris-flow | 3 | 15 | 12 |
| hris-platform | 3 | 20 | 17 |

权限点已用 `scripts/seed_rbac_from_source.py` 同步至 auth_db 并授予 admin 角色
（源码权限点从 148 增至 160）。

端到端验证（起 hris-org 直连 8102，手工构造 `X-Tenant-Id` / `X-User-Id` /
`X-User-Perms` 头）：

- 不带 `X-User-Perms` 调 `GET /org/depts` → `code=20403 无权限`
- 带 `org:dept:read` 调同一端点 → `code=0`，正常返回部门树
- 仅 `org:position:read` 调 `DELETE /org/positions/999` → `20403`
- 带 `org:position:write` 调同一端点 → 进入业务逻辑（返回「岗位不存在」）

### 7.2 部分修复：ORG 与 EMP 的管理界面

§2.1 指出的「后端完整但零前端界面」，已补 9 个页面：

| 模块 | 页面 | 路由 |
|---|---|---|
| ORG | 法人主体 / 部门管理 / 岗位 / 职位 / 职级 / 职级带 / 编制 | `/admin/org/*` |
| EMP | 员工花名册 / 合同到期预警 | `/admin/employee/*` |

实现说明：
- 5 个目录类页面（契约中同为 `CatalogResponse`）抽象为
  `components/admin/CatalogCrudPage.vue` 薄包装，避免五份代码各自漂移
- 编制页的 `PUT /org/headcounts` 是 upsert（主键为 deptId+positionId+period
  三元组，无路径 id），编辑表单保留这三个字段
- 花名册不提供「新建」与「删除」：新员工走入职流程（含编制校验与状态机），
  离职走状态机而非物理删除
