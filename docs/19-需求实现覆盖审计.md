## 5. 方法论与局限

**判定依据（四类证据，缺一即降级）**
1. API 端点：契约 `docs/openapi.gen.json` 中是否存在对应 path + method
2. 数据表：`docs/db/schema-mysql.sql` 中是否存在承载该能力的表与关键字段
3. 业务逻辑：Service 层是否存在对应方法与守卫（如状态机、编制校验、密域权限）
4. 前端可用性：`frontend/src/views/` 与管理端菜单注册表是否存在入口

**局限（必须说明）**
- **静态审计，未做功能实测**。例如"算薪引擎"判定为已实现，依据是 `payroll-preview` 端点 + `PayrollPreviewService` 取数逻辑存在，但未验证计算结果与考勤/社保取数的正确性。
- **"部分实现"含主观判断**。如 ORG-F-004 判定为部分，依据是缺"草稿版本"状态机；若产品侧认为"生效日期 + 快照"已足够，则应计为已实现。
- **跨模块实现未重复计数**。ORG-F-016（数据权限范围定义）在 `hris-auth` 的 `AuthDataScope` 实现，计为已实现；EMP-F-025（敏感字段脱敏）同理。

### 7.1 已修复：一期模块的权限校验缺口（安全）

审计时未列此项，是在动手补页面时发现的——`PermAspect` 只拦截标注了
`@RequirePerm` 的方法（`@Around("@annotation(requirePerm)")`），无注解的端点
完全不做权限校验。而当时全仓 302 个 `@RequirePerm` 中，二期（代码生成）占 290 个，
一期手写模块合计仅 12 个。

后果：任何持有效 JWT 的用户都能创建法人主体、删除岗位、改编制配额、审批他人单据、
改系统字典——网关只验签，不做垂直越权拦截。

| 模块 | 修复前 | 修复后 | 新增 |
|---|---|---|---|
| hris-org | 2 | 27 | 25 |
| hris-employee | 4 | 13 | 9 |
| hris-flow | 3 | 15 | 12 |
| hris-platform | 3 | 20 | 17 |

权限点已用 `scripts/seed_rbac_from_source.py` 同步至 auth_db 并授予 admin 角色
（源码权限点从 148 增至 160）。

端到端验证（起 hris-org 直连 8102，手工构造 `X-Tenant-Id` / `X-User-Id` /
`X-User-Perms` 头）：

- 不带 `X-User-Perms` 调 `GET /org/depts` → `code=20403 无权限`
- 带 `org:dept:read` 调同一端点 → `code=0`，正常返回部门树
- 仅 `org:position:read` 调 `DELETE /org/positions/999` → `20403`

### 7.4 审计结论的两处更正（自查发现）

在动手补 PLT 页面时复核代码，发现原审计有两处判定不准确。记录在此以免误导后续排期：

**更正 1：PLT-F-005/F-006 报表中心 — 由「未实现」校准为「部分实现」**

原审计在 §5 的 P1 未实现清单中把报表中心列为未做。复查后判定为**部分实现**而非「已实现」：
- 报表定义维护链路完整：`ReportController` 提供 `GET/POST /plt/reports/defs`、
  `PUT/DELETE /plt/reports/defs/{id}`、`GET/POST /plt/reports/exports`；
  `ReportService` / `ExportTaskService` 与表 `sys_report_def` / `sys_export_task` 齐备，
  前端「报表定义」「导出记录」两页与「预置报表目录」接口（`GET /plt/reports/catalog`，五类主题）已补上。
- **异步导出此前只是写入 `PENDING`，无执行器推进**——`ExportTaskService` 的完成/失败回调全仓无调用方，
  任务永远停在待处理；该缺口属"业务闭环未通"，不能算已实现。
- 订阅 / 定时发送报表等子能力仍未做；依赖只读聚合库的统计报表同理。

故维持"部分实现"：主链路 API + 前端 + 目录具备，执行器与订阅能力缺失（执行器缺口已由 §7.5 的调度中心补齐）。

**更正 2：PLT-F-011 任务调度 — 由「未实现」改为「已实现」**

原审计判定为完全未实现（仅有表 `sys_scheduler_task_registry` 及 Entity/Mapper，无 `@Scheduled`、
无 xxl-job 依赖、无 `/plt/scheduler*` 端点、表未被读取）。**该判定现已过时**：调度中心已在本轮落地
（详见 §7.5），表被 `SchedulerRegistry` 实际读取并驱动动态 cron 注册，故更正为**已实现**。

> 注：§4.1 仍保留"完全未实现"的原判定作为可追溯快照，本更正为其最新结论。

### 7.5 本轮实际交付：调度中心 + 报表异步导出执行器

为闭环 §7.4 两处更正，本轮落地了 PLT-F-011 调度中心，并让报表导出真正跑起来：
- `hris-platform` 新增编程式调度：`ThreadPoolTaskScheduler` + `CronExpression` 动态注册 / 启停 / 立即执行 / 失败重试（最多 3 次），
  新增执行日志表 `sys_scheduler_task_log`；`SchedulerController`（`@RequirePerm plt:scheduler:read/write`）提供任务与日志管理端点。
- 首个真实任务 `EXPORT_TASK_DISPATCH`（`ExportTaskDispatchHandler`）：扫描 `PENDING` 导出任务 → `RUNNING` → 生成文件 → 完成回调，
  失败 `FAILED` 并进入重试；MinIO 不可用时 **fail-closed 置 FAILED**（不伪造 DONE）。
- 调度线程无租户上下文，执行前按注册项 `setTenantId`、finally `clear`，避免跨租户。
- 前端新增「调度中心」页（`/admin/platform/scheduler`）与执行日志面板。
- 决策：**不引入 XXL-JOB**，单应用编程式调度已满足当前规模，避免新增中间件与运维负担。

两个口径都有价值：宽口径回答"主链路能不能跑"（能），严口径回答"需求是否完整满足"（大量子能力缺失）。

### 8.3 五条系统性断链（跨模块根因，修复性价比最高）

1. **审批回调全断（最重）**：flow 审批完成后到业务域的回调三路全断——① `EventOutboxService.dispatchPending`
   仅落表不发送（RocketMQ producer 未接入）；② flow 无 att/emp 的 Feign client（仅 OrgClient）；
   ③ att 的 `/internal/att/approval-callback` 与 emp 的 `LifecycleCaseService.approve` **全仓无生产调用方**。
   后果：ORG/EMP/ATT **所有审批单据永远停在 PROCESSING**——请假不扣额度、生命周期单不生成待生效事务、
   组织调整 PENDING 永不更新。前端"我的审批"只调 flow 端点，审批动作与业务状态完全脱钩。
2. **事件总线断链**：FLW-F-012 全仓无 RocketMQ 依赖与 producer，outbox 事件永远 PENDING，死信与告警无载体。
3. **密文列存明文**：`emp_employee.cert_no_cipher/mobile_cipher`、`cmp_payslip.net_pay_cipher` 等全部
   `*_cipher` 列直接存调用方传入的明文（代码注释自认"MVP 明文占位"）；叠加 **RCS 候选人 mobileCipher
   明文直出**（CandidateDtos.java 响应无 mask）与 **跨域语义错位**（OfferOnboard 把 candidate.mobileCipher
   当明文传 employee，接入真加密后整条链路静默脏数据）。docs/20 §4.2 的等值查询失效链同样适用。
4. **审计落库断裂**：`AuditLogService.append` 全仓零调用方，`AuditLogAspect` 只写本地 logback——
   sys_audit_log 是空表，查询页守卫守护的是空数据。登录/薪酬查看/导出/权限变更均不入库（P0 合规）。
5. **二期生成器骨架**：RCS/CMP/PRF/KBD 的 Service 绝大多数为 `gen_phase2.py` 产出的纯 CRUD
   （RCS 13 个 Service 12 个骨架；CMP 14 个仅 2 个手写；PRF 17 个全部骨架、零业务守卫）——
   「有表有接口」≠「需求已实现」。

### 8.5 实现有问题清单（严口径三类阻断，按严重度）

**高危（数据安全/完整性）**
1. 候选人手机号明文外泄：CandidateResponse 直出 mobileCipher（实为明文），持 rcu:candidate:read 即可拉全量。
2. 密文列存明文贯穿 EMP/CMP（详见 §8.3-3），规格"传输全程加密"在存储层不成立。
